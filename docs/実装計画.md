## 1. カラーピッカーを色相環型に変更 ✅ 実装済み (2026-07-20)

### 現状と問題

色を選ぶUIは現状2箇所ある。検索画面 `lib/screens/search_screen.dart` の `_openColorPicker()`(行129-165)と、テスピ編集画面 `lib/screens/test_piece_edit_screen.dart` の `_addColor()`(行643-683)である。どちらも `flutter_colorpicker` パッケージの標準 `ColorPicker` ウィジェット(色相スライダー+彩度/明度の矩形)を `AlertDialog` に入れて使っている。ユーザーはこれを色相環型にしたいと考えている。

ただし、テスピ編集画面のカラーピッカーは第4章のスポイト刷新で**廃止される**(スポイトが代替となる。ユーザー確定)。したがって色相環への差し替えは**検索画面の1箇所のみ**行う。

### 方針と変更内容

同じ `flutter_colorpicker` パッケージ(導入済み、`^1.1.0`)に色相環型の `HueRingPicker` が含まれているため、依存追加なしでウィジェットを差し替えるだけでよい。`HueRingPicker` は外周が色相環、中央が彩度/明度の矩形になっており、彩度の低い色が多い釉薬でも問題なく選べる。

`search_screen.dart` の `_openColorPicker()` 内の `ColorPicker` を `HueRingPicker` に差し替える。現状の `enableAlpha: false`、`displayThumbColor: true` は維持する。`hexInputBar` は `HueRingPicker` にも同名パラメータがあるのでそのまま渡す。ダイアログの体裁(タイトル、キャンセル/決定ボタン)は変更しない。

### 検証

検索画面でダイアログを開き、色相環での選択・hex入力・決定/キャンセルが機能することを目視確認する。

## 2. 検索結果の並び替え ✅ 実装済み (2026-07-20)

### 現状と問題

検索のフィルタロジックは純関数 `filterTestPieces`(`lib/services/test_piece_search.dart`、行23-34にシグネチャ)に抽出されており、現状の並び順はこの関数が暗黙に決めている。具体的には、テキスト検索時は「釉薬名・タグ等にマッチした群(primary)が先、原料名のみにマッチした群が後」という連結順(行49-102)、色検索時は色差ΔEの昇順(行138)、条件なしなら入力リスト順(= Firestore クエリの createdAt 降順)である。ユーザーがこの並びを変える手段は存在しない。

### 方針

並び順を表す enum を新設し、`filterTestPieces` に引数として渡せるようにする。UIは検索結果ヘッダに置く。

`lib/services/test_piece_search.dart` に以下を追加する。

```dart
enum TestPieceSortOrder {
  relevance,      // 現状の順序 (テキストマッチ優先度、条件なしなら新着順)
  newest,         // createdAt 降順
  oldest,         // createdAt 昇順
  colorDistance,  // 色検索時のみ有効: ΔE 昇順
}
```

`filterTestPieces` に `TestPieceSortOrder sortOrder = TestPieceSortOrder.relevance` を追加し、関数末尾の return 直前でソートを適用する。実装上の注意が2つある。第一に、既存の色検索パス(行115-140)は ΔE 昇順ソートを内蔵しているが、これを「`colorDistance` が指定されたときのソート」として定式化し直すこと。ΔE値はフィルタ通過判定にも使うため、タプル `(TestPiece, double)` を保持する既存構造は活かせる。第二に、`relevance` はテキスト検索の primary/material 連結順を意味するので、`relevance` 指定時はソートを何もしない(現状の挙動そのまま)。`newest`/`oldest` は `createdAt` で安定ソートする。

検索画面 `lib/screens/search_screen.dart` 側は、State にソート状態フィールドを追加し(既存の条件フィールド群、行33-43の並び)、デフォルトを次のように動的に決める: 色条件がある場合は `colorDistance`、ない場合は `relevance`。色条件を追加・削除したタイミングでデフォルトに戻すのではなく、**ユーザーが明示的に選んだソートは条件変更後も維持**し、無効な組み合わせ(色条件がないのに `colorDistance`)になった場合のみ `relevance` にフォールバックする。

UIは `_buildSearchResults`(行705-799)のヘッダ行(「検索結果」ラベルとグリッド/リスト切替ボタンがある行714-724)に `PopupMenuButton<TestPieceSortOrder>`(アイコン `Icons.sort`、選択中の項目に `CheckedPopupMenuItem` のチェック)を追加する。`colorDistance` の項目は色条件があるときだけメニューに出す。

### 検証

`test/` に `filterTestPieces` のソート挙動のユニットテストを追加する(newest/oldest の順序、色検索時の colorDistance、relevance が既存順を壊さないこと)。既存の filterTestPieces テストがあれば引数追加に追従させる。

## 3. ホームタブの自動グループ表示 ✅ 実装済み (2026-07-20)

### 現状と問題

テスピ一覧(ホームタブ、`lib/screens/test_piece_list_screen.dart`)は `TestPieceGrid`(`lib/widgets/test_piece_grid.dart`)による単一グリッドで、並び順は `lib/repositories/test_piece_repository.dart` の `orderQuery`(createdAt 降順、行18-21)のみ。件数が増えると目的のテスピを探しにくい。ユーザーは素地土別・色味別などの切り口でまとまって見えることを望んでいる。

### 方針の全体像

グループキー(なし / 素地土 / 焼成雰囲気 / 焼成プロファイル / 色味)を設定として持ち、「なし」以外が選ばれたらセクションヘッダ付きのグリッドで表示する。データモデルの変更は不要で、グループ化はクライアント側の純関数で行う。グループ化対象は高々数百件なので build 内の同期計算で十分であり、専用の Riverpod プロバイダは作らない。

### 新規ファイルと役割

**`lib/models/test_piece_group_key.dart`** — グループキーの enum。表示ラベル(なし/素地土/焼成雰囲気/焼成プロファイル/色味)を getter で持つ。**デフォルト値は「なし」**であり、設定が保存されていない初回起動時は必ず従来通りの単一グリッド表示になる。SharedPreferences への永続化は enum の `name` 文字列で行い、読み込み時は `values.firstWhere(orElse: なし)` で解決する(enum の並び替えに耐えるため index は使わない)。

**`lib/utils/test_piece_grouping.dart`** — グループ化の純関数。シグネチャは次を想定する。

```dart
class TestPieceGroup {
  final String label;
  final List<TestPiece> pieces;
}

List<TestPieceGroup> groupTestPieces({
  required List<TestPiece> pieces,        // createdAt降順で渡ってくる
  required TestPieceGroupKey key,
  required Map<String, Clay> clayMap,
  required Map<String, FiringAtmosphere> atmosphereMap,
  required Map<String, FiringProfile> profileMap,
});
```

各グループ内の並びは入力順(createdAt 降順)を維持し、空のグループは返さない。素地土・雰囲気・プロファイルによるグループ化では、IDがnull/空のものは「未設定」、IDはあるがマスタに存在しない(削除済み)ものは「不明」というグループに入れ、どちらも末尾に置く。名前のあるグループは名前昇順に並べる。

**「色味」の分類ロジック**もこのファイルに置く。方式はユーザーと合意済みで、汎用の色相ベース9分類(赤系/黄系/緑系/青系/紫系/茶系/白/グレー/黒)+「色データなし」で開始し、閾値は定数化しておいて使用感に応じて調整する。釉薬語彙での分類(青磁系・飴系など)は将来の調整候補。

分類は CIELCh 空間で行う。colorData は既に CIELAB(`lib/models/lab_color.dart`)で保持されているため、彩度 `C* = sqrt(a² + b²)` と色相角 `h = atan2(b, a)`(度に変換して [0, 360) に正規化)の2行で到達でき、sRGB への往復変換誤差が入らない。HSV は使わない。代表色は colorData のうち `percentage` 最大のエントリとする(スポイトで手動追加した色は percentage=0 なので、全て0の場合は先頭を使う)。判定は次の順で行う。

1. `C* < 12` なら無彩色: `L ≥ 75` → 白、`L ≤ 30` → 黒、それ以外 → グレー
2. `h ∈ [30, 110)` かつ `L < 50` → 茶系(暗い橙〜黄は飴釉・鉄釉に相当するため、赤・黄の判定より先に評価する)
3. `h ∈ [345, 360) ∪ [0, 45)` → 赤系
4. `h ∈ [45, 110)` → 黄系
5. `h ∈ [110, 200)` → 緑系
6. `h ∈ [200, 300)` → 青系
7. `h ∈ [300, 345)` → 紫系

グループの表示順は固定配列「赤→黄→緑→青→紫→茶→白→グレー→黒→色データなし」とする。

**`lib/widgets/sectioned_test_piece_grid.dart`** — セクション付きグリッド。構造は次の通り。

```
RefreshIndicator
└ CustomScrollView(physics: AlwaysScrollableScrollPhysics)
  ├ グループごとに SliverMainAxisGroup(slivers: [
  │    SliverToBoxAdapter(ヘッダ: グループ名 + 件数),
  │    SliverPadding(sliver: SliverGrid.builder(...)),
  │  ])
  └ SliverToBoxAdapter(SizedBox(height: 80))  // FABとの重なり回避
```

shrinkWrap した GridView を ListView に縦積みする方式は採用しない。その方式では各グリッドの全アイテムが即時レイアウトされて遅延ビルドが効かなくなり、数百件のサムネイル画像リクエストが一斉に走るためである。CustomScrollView + SliverGrid なら画面外のセクションもアイテム単位で遅延ビルドされる。セクションヘッダのピン留め(SliverPersistentHeader)は実装コストに対して益が小さいため初版では見送る。

### 既存ファイルの変更

**`lib/widgets/test_piece_grid.dart`** — グリッドのデレゲート計算(`SliverGridDelegateWithMaxCrossAxisExtent` を組み立てている行41-47付近)とカード生成(itemBuilder の本体)を、`static SliverGridDelegateWithMaxCrossAxisExtent gridDelegateFor(double availableWidth, int crossAxisCount)` と `static Widget buildCard(TestPiece, {各種マップ})` として抽出する。既存の build はこの2つを呼ぶだけにし、公開APIとコンストラクタは変えない。これにより検索画面(`search_screen.dart` 行752 で使用)には一切影響を与えず、`SectionedTestPieceGrid` が一覧グリッドと完全に同じ見た目のセルを描画できる。

**`lib/services/settings_service.dart`** — `gridCrossAxisCount` と同じパターン(SharedPreferences 読み書き + `notifyListeners()`)で `testPieceGroupKey` の getter / setter を追加する。

**`lib/screens/test_piece_list_screen.dart`** — `ref.watch(settingsServiceProvider)` は列数取得のために既に行っているので、そこから groupKey を読み、`none` なら従来通り `TestPieceGrid`、それ以外なら `groupTestPieces()` の結果を `SectionedTestPieceGrid` に渡す分岐を入れる。素地土等のマップは既存の `clayMapProvider` / `firingAtmosphereMapProvider` / `firingProfileMapProvider` を watch する。

**`lib/screens/main_tab_screen.dart`** — `_buildAppBarActions()` の `case _MainTab.testPieces:` は現在 `const []` を返している(行326-328)。ここにグループ切替の `PopupMenuButton<TestPieceGroupKey>`(アイコン `Icons.workspaces_outlined`、tooltip「グループ表示」、選択中項目に `CheckedPopupMenuItem`)を追加する。コードの置き場所は、原料タブが `MaterialsListScreen.buildActions(...)` という static メソッドを AppBar に差し込んでいる前例に倣い、`TestPieceListScreen` に static メソッドとして置き、main_tab_screen からはそれを呼ぶ。

### 検証

`test/utils/test_piece_grouping_test.dart` を新設し、色相バケツの境界値(C*=12近傍、h=45/110/200/300 の境界、茶系のL閾値、percentage全0時の代表色選択)と、未設定/不明グループの振り分けをテストする。実機では、グループ切替 × グリッド列数変更 × プルリフレッシュ × F5 × FAB の組み合わせが壊れないことを確認する。

## 4. スポイト機能の刷新(本計画の最重量) ✅ 実装済み (2026-07-20)

実装後の追加対応: multi モードのスポイト画面に呼び出し元の登録済み色を参照表示する `existingColors` パラメータを追加した(重複チェック用、ユーザー要望)。Functions はデプロイ済み。

### 要望の本質

やりたいことリストの「やっぱテスピ編集画面でスポイトやりたい」の本質は次の通り(ユーザー確認済み)。

> 編集画面でテスピの色を手動追加する際、カラーピッカーからソラで(元画像を見ずに)選ぶ現状の方式はあまりにも不親切。最低でも元画像を一緒に表示するか、理想的には画像からスポイトで選択できるようにしたい。

さらに、既存のスポイト実装(詳細画面の検索用スポイト)自体に以下のUX問題があることが指摘されている。

- **状態が見えない**: スポイトモード中かどうかが見た目でほぼ判別できない(ボタンのアイコンが outline に変わるだけ)。
- **修正できない**: タップした瞬間に確定してしまい、選んだ場所の微調整・選び直しができない。
- **結果として非常に使いにくい。**

これらは既存実装の小改修では解決できず、スポイトのウィジェットを自前で書く必要がある。本章が今回の実装で最も重い。

### 既存実装の構造(置き換え対象)

詳細画面 `lib/screens/test_piece_detail_screen.dart` の現行スポイトは、画像を `RepaintBoundary(key: _imageKey)` で包み(行228-229)、タップ時に `boundary.toImage()` で**画面表示をラスタライズし**、`toByteData(rawRgba)` からタップ座標のピクセルを読む方式である(`_handleImageTap`、行504-543)。取得した色で即 `SearchScreen(initialColor:)` へ遷移する。この方式には UX 問題に加えて構造的な欠点がある: 画面のラスタライズ結果を読むため、画像読み込み中にタップするとローディングスピナーの色を拾うし、表示解像度でしかサンプリングできない。関連コードはモードフラグ `_isEyedropperActive`(行36)、GestureDetector の分岐(行223-236)、トグルボタン(行237-272)。刷新後、これらはすべて削除する。

### 解決方針の全体像

色選択専用のフルスクリーン画面 `ColorPickScreen` を新設する(ユーザー確定: 編集画面の小さいプレビュー上でのインライン選択ではなく専用画面)。設計の柱は次の4つ。

1. **画面のラスタライズをやめ、画像そのものをデコードしてサンプリングする。** 画像を一度だけ `ui.Image` にデコードし、`toByteData(rawRgba)` でピクセルバッファを保持する。以後のサンプリングはこのバッファへの座標計算だけで済み、UIオーバーレイの影響を受けず、原寸解像度で色を拾える。
2. **マーカー+常時ルーペ+ライブ色プレビューで「今どこの何色を選んでいるか」を常に可視化する。** 専用画面である時点で「スポイトモード中か分からない」問題は消滅する。
3. **確定は明示的な操作で行い、確定前の微調整を自由にする。**
4. **入力デバイスで操作系を分ける(ユーザー指定)。** タッチではドラッグ中の指が選択点を隠すため、マーカーは「タップ位置へジャンプ」ではなく**スワイプによる相対移動**とし、決定ボタンで確定する。マウスではポインタ自体をマーカーとして扱い、**ホバー中は常にポインタ位置の色をルーペ+プレビューに表示し、クリックで確定**する。判定はプラットフォームではなくポインタイベントの `PointerDeviceKind` で行う(タッチ液晶付きWindowsでもマウスとタッチそれぞれが自然に動く)。

### 画面仕様: ColorPickScreen

**新規 `lib/screens/color_pick_screen.dart`**

```dart
enum ColorPickMode { single, multi }

class ColorPickScreen extends StatefulWidget {
  final ImageProvider imageProvider;
  final ColorPickMode mode;
}
// pop の戻り値: single → Color?(キャンセル時 null) / multi → List<Color>(空可)
```

呼び出し側は `ImageProvider` を渡すだけでよい。編集画面で新画像を選んだ直後なら `MemoryImage(_newImageBytes)`、既存画像なら `CachedNetworkImageProvider(imageUrl)`(キャッシュを `AppNetworkImage` と共有できる)を渡す。

画面のレイアウトは次の3層構造とする。

- **画像レイヤ**: `InteractiveViewer`(`TransformationController` 保持)の子として画像を表示。ピンチ/ホイールでズームできる。
- **オーバーレイレイヤ**: マーカー(十字線+小円)を `Stack` で InteractiveViewer の**上**に描く。マーカー位置は画像ピクセル座標で保持し、画面座標へは `controller.value` で変換して描画する(こうするとズームしてもマーカーの線の太さ・サイズが画面上で一定に保たれる)。controller に listener を付けてズーム/パンのたびに再描画する。
- **情報パネル**: 画面上部に固定配置。ルーペ(後述)、選択色のスウォッチ、hex値を常時表示する。下部にはモードに応じた操作列を置く(後述)。

**ルーペは自前の CustomPainter で描く。** Flutter 標準の `RawMagnifier` は画面のレンダリング結果を拡大するものでオーバーレイも写り込むが、こちらはデコード済みピクセルバッファを持っているので、マーカー周辺(たとえば15×15ピクセル)をバッファから読んで拡大描画するほうが正確で、プラットフォーム差もない。中心ピクセルに十字を描く。

**タッチ操作**(`PointerDeviceKind.touch` / `stylus`):

- 1本指ドラッグ = マーカーの相対移動。指の移動量(画面px)を現在のズーム倍率で割って画像ピクセル座標系の移動量に変換し、マーカーに加算する。画像の外にはクランプする。タップでマーカーはジャンプ**しない**(ユーザー指定)。
- 2本指 = ズームとパン。`InteractiveViewer` は `panEnabled: false, scaleEnabled: true` とする。こうすると1本指ドラッグが InteractiveViewer に食われずマーカー移動に使え、2本指のスケールジェスチャ(焦点移動によるパン含む)は InteractiveViewer が処理する。
- 確定は下部の「決定」ボタン。
- マーカーの初期位置は画像中央。

**マウス操作**(`PointerDeviceKind.mouse`):

- `MouseRegion.onHover` でポインタ位置を追跡し、ポインタ位置をそのままマーカーとして扱う。ルーペと色プレビューはホバーに追随してライブ更新する。
- クリック(押下から移動閾値以内で離す)= その位置で確定。ドラッグ(閾値を超える移動)はパンとして扱う。ホイールはズーム(InteractiveViewer が処理)。
- マウス操作時は下部の「決定」ボタンは不要だが、UIの分岐を減らすため表示したままでよい(押せば現在のマーカー位置で確定)。

**確定フロー**(ユーザー確定: 連続追加可):

- `multi` モード(編集画面用): 確定するたびに色を画面内のリストに追加し、画面に留まる。追加済みの色は下部にチップ列で表示し、その場で個別削除できる。「完了」ボタンで追加済みリストを `Navigator.pop` の戻り値として返す。AppBar の戻るも「完了」と同じ扱いとし(破棄しない)、意図しない全損を防ぐ。捨てたい色はチップ削除で対応できる。
- `single` モード(詳細画面の検索用): 確定した時点で `Color` を返して pop する。戻る操作は null(キャンセル)。

### サンプリング基盤: ImagePixelSampler

**新規 `lib/utils/image_pixel_sampler.dart`**

`ui.Image` から `toByteData(format: rawRgba)` で取り出したバッファと幅・高さを保持し、`Color? colorAt(int x, int y)`(範囲外は null)を提供する小さなクラス。オフセット計算は `(y * width + x) * 4`。現行 `_handleImageTap` の読み取り部と同じロジックだが、画面のラスタライズ結果ではなく**デコードした画像そのもの**に対して行う点が違う。将来のノイズ対策として近傍平均(3×3等)を定数で切り替えられる形にしておくが、初版は1ピクセル読みでよい(ルーペがあるので狙って拾える)。

`ImageProvider` から `ui.Image` への解決は `ImageStream`/`ImageStreamListener` で行い、解決中はスピナー、失敗時はエラー表示と操作無効化を行う。デコード済みバッファのメモリは 1500px 上限の画像(編集画面の ImagePicker 設定)で高々 9MB 程度であり問題ない。

座標変換は「ビューポート座標 ⇄ シーン座標(`controller.toScene()`)⇄ 画像ピクセル座標(画像の表示スケール係数で除算)」の2段で行う。この変換とサンプリングはユニットテスト対象とする。

### 呼び出し側の変更

**編集画面 `lib/screens/test_piece_edit_screen.dart`**: 色セクション(`_buildColorSection`、行603-615)の「色を追加」を「スポイトで追加」ボタンに置き換える。画像がある場合(新画像バイトまたは既存URL)のみ有効。タップで `ColorPickScreen`(multi)へ遷移し、戻り値の各色を `LabColor.fromColor(color)` → `_colorData.add(percentage: 0)` + `_markAsDirty()` で反映する(既存の `_addColor` の追加経路、行679と同じ)。**既存のカラーピッカーダイアログ(`_addColor`)は削除する**(ユーザー確定。ソラで色を選ぶ方式そのものが不親切の原因であり、スポイトが完全な代替となる)。画像がないテスピでは色を手動追加できなくなるが、colorData は本来画像の解析結果であり画像なしテスピに色を登録する意味が薄いため許容する。

**テストピース詳細画面 `lib/screens/test_piece_detail_screen.dart`**: スポイトボタンの押下先を `ColorPickScreen`(single、`CachedNetworkImageProvider(imageUrl)`)への遷移に変え、返ってきた色で `SearchScreen(initialColor:)` へ push する。旧実装(`_isEyedropperActive`、GestureDetector 分岐、トグルボタンの黒背景丸ボタン、`_handleImageTap` 行504-543、スポイト専用の `RepaintBoundary`/`_imageKey`)は削除する。Hero タグと全画面表示(スポイト無効時の onTap)は維持すること。

### colorData 保存契約の変更(必須の付随作業)

現状の保存契約(spec.md §5)は「新画像がある場合、クライアントは `colorData: []` を明示的に送り、Cloud Functions が解析結果で**無条件に上書き**する」である(`_saveTestPiece` 行170 の `colorData: hasNewImage ? [] : List.of(_colorData)`、および `functions/image_pipeline.py` 行239-243 の `update()`)。この契約のままだと、**新画像を選んでスポイトで色を追加しても、保存時に [] が送られ、さらに Functions が解析結果で上書きするため、ユーザーの色が二重に消える**。契約を次のように変更する。

- **クライアント**: `_pickImage()` で新画像が確定したタイミング(クロップ結果を反映する行111-118)で `_colorData` を空にクリアする(旧画像の解析色は新画像には無意味なため)。`_saveTestPiece` は分岐を削除し、常に現在の `_colorData` を送る。ユーザーが何も追加していなければ自然に `[]` が送られる。
- **Functions**(`image_pipeline.py`): 書き戻しをトランザクション化し、**ドキュメントの colorData が非空なら colorData の書き込みをスキップ**(imageUrl / thumbnailUrl のみ更新)、空なら解析結果を書く。素の read→update ではクライアント保存との間に race が生じるため、必ず `@firestore.transactional` で読み判定と書き込みを不可分にする。

この契約でのシナリオ整理: 新画像+スポイト色なしで保存 → [] が送られ Functions が解析結果を書く(従来通り)。新画像+スポイト色ありで保存 → 色が送られ Functions はスキップ(新機能の本命)。Functions が書き戻した**後**にユーザーが色を編集して保存 → ユーザーの値で上書き(後勝ち=ユーザー意図優先で正しい)。

**デプロイ順序に注意**: Functions を先にデプロイすること。旧クライアント+新 Functions は「[] が送られて解析結果が書かれる」だけで無害だが、新クライアント+旧 Functions は「スポイト色が解析結果に上書きされる」期間を生む。

spec.md §5 の契約記述と §2 の `process_uploaded_image` の説明もこの内容に書き換える(第7章)。

### 実装ステップ

1. `ImagePixelSampler` とビューポート⇄ピクセル座標変換をユニットテスト付きで実装する。
2. `ColorPickScreen` を実装する(まず single モードのマウス操作 → タッチの相対移動 → multi モードの順に積み上げると確認しやすい)。
3. テストピース詳細画面を新スポイトに載せ替え、旧実装を削除する。
4. 編集画面に「スポイトで追加」を組み込み(`_addColor` のカラーピッカーダイアログは削除)、`_pickImage` のクリアと `_saveTestPiece` の分岐削除を行う。
5. `image_pipeline.py` をトランザクション化し、**クライアント変更のリリース前にデプロイする**。

## 5. テスピ情報まとめ画像のPNG書き出し+共有 ✅ 実装済み (2026-07-20)

### 要望と方針

「釉薬情報、焼成情報、素地土の情報、テスピ情報を1画面にまとめたものをサクッと共有したい」に対し、ユーザーと合意した形は「1枚のPNGに合成し、Android では共有シート、Windows/macOS では名前を付けて保存」である。

実装方式は**共有プレビュー画面 + RepaintBoundary キャプチャ**とする。オフスクリーンで RenderTree を手組みする方式は、ネットワーク画像・フォント・テーマの解決をすべて自前管理する必要があり複雑なわりに利点がない。プレビュー画面方式なら書き出される絵をユーザーが事前確認でき、既存の表示ウィジェット(`RecipeTable`、`InfoTile`、`FiringChart`)をそのまま再利用できる。

### 画面仕様

**新規 `lib/screens/test_piece_share_screen.dart`** — `TestPieceShareScreen(testPiece)`。関連データ(釉薬・素地土・雰囲気・プロファイル・原料)はコンストラクタで渡さず、アプリの流儀通り各マッププロバイダを watch して解決する。

キャプチャ対象は論理幅800px固定のカードとし、次の構造で組む。

```
Scaffold
├ AppBar('共有プレビュー', actions: [共有/保存ボタン])
└ SingleChildScrollView
  └ Center → FittedBox(fit: scaleDown)      // 狭い画面では縮小表示するが、
    └ RepaintBoundary(key: _captureKey)      // FittedBoxの変換はboundaryの外なので
      └ Theme(data: ライトテーマ固定)         // キャプチャは常に800px幅の等倍
        └ Material(color: surface)           // 透過PNG防止のため背景を明示的に塗る
          └ SizedBox(width: 800) → Column [
              釉薬名(見出し) + 作成日,
              AspectRatio(1:1, 画像, fit: contain),
              色見本スウォッチ列,
              調合表 (RecipeTable 再利用),
              追加釉薬・素地土・焼成雰囲気 (InfoTile 再利用),
              焼成プロファイル名 + FiringChart,
              備考,
            ]
```

配色は**常にライトテーマで出力する**(ユーザー確定)。アプリがダークテーマでも、`RepaintBoundary` 内側を `Theme(data: ライト)` で包むことで書き出しだけライトになる。共有相手の環境や印刷を考慮した選択である。

色見本はテストピース詳細画面(`test_piece_detail_screen.dart`)の `_buildColorSwatches`(行417-447、percentage>5 のみ丸スウォッチ表示)を **`lib/widgets/common/color_swatch_row.dart`** に抽出して共用する。タップ動作はコールバックを optional にし、テストピース詳細画面では検索遷移、共有画面では無効とする。

### キャプチャと画像読み込み待ち

キャプチャは `_captureKey` の `RenderRepaintBoundary.toImage(pixelRatio: 2.5)` → `toByteData(png)` で行う。撮影前に2つの待ちが必要である。第一に、テスピ画像は `CachedNetworkImageProvider(imageUrl)` に対する `precacheImage`(10秒タイムアウト付き)で読み込み完了を待ってから共有ボタンを有効化する。`AppNetworkImage` と同じ provider を使うためキャッシュが共有される。タイムアウトや失敗時は壊れ画像アイコンのまま撮影可能とする(オフラインでも機能を殺さない)。第二に、キャプチャ直前に `await WidgetsBinding.instance.endOfFrame` で1フレーム待ち、「precache は済んだが画面に反映される前」のフレームを掴む事故を防ぐ。

`FiringChart`(`lib/widgets/firing_chart.dart`)は fl_chart の `LineChart` を直接返しており、データ設定時の補間アニメーション中にキャプチャすると中間フレームが写る恐れがある。`FiringChart` に `Duration duration` パラメータを追加して `LineChart` に渡し(デフォルトは現行挙動を維持する値)、共有画面では `Duration.zero` を指定する。既存の呼び出し2箇所は無変更で通る。

### 共有/保存の分岐

**新規 `lib/utils/png_exporter.dart`** に、キャプチャ(`captureBoundary`)とエクスポート(`export`)を画面から分離して置く。エクスポートはプラットフォームで分岐する。

- **Android / iOS**: `share_plus` を新規依存として追加し、`SharePlus.instance.share(ShareParams(files: [XFile.fromData(bytes, mimeType: 'image/png', name: fileName)]))` で共有シートを開く。share_plus 11系では旧 `Share.shareXFiles` が deprecated である点に注意。
- **Windows / macOS / Linux**: `share_plus` は呼ばない。デスクトップの共有UIは共有先が乏しく、Windows ではバージョンによって未実装例外を投げた経歴もある。既存依存の `file_picker`(^10.3.3)の `FilePicker.platform.saveFile` でパスを取得し、**自前で `File(path).writeAsBytes(bytes)` する**(デスクトップの saveFile はパスを返すだけでファイルを書かない)。キャンセル(null)は SnackBar で「キャンセルしました」等を出さず静かに戻ってよい。

ファイル名は釉薬名から Windows 禁止文字 `\ / : * ? " < > |` を除去し、`{釉薬名}_{yyyyMMdd}.png` とする。エクスポート中は `_isExporting` フラグでボタンを無効化し二重実行を防ぐ。この操作は Firestore への保存ではないため楽観的 pop の対象外であり、完了を await して成否を SnackBar で通知する。

### 入口と変更ファイル

入口は**テストピース詳細画面**(`lib/screens/test_piece_detail_screen.dart`。釉薬詳細画面等ではない)の AppBar(actions、行101-108付近)に共有アイコン(`Icons.share`、tooltip「共有画像を作成」)を追加し、`TestPieceShareScreen` へ push する。

変更まとめ: 新規は `test_piece_share_screen.dart` / `png_exporter.dart` / `color_swatch_row.dart` の3ファイル。変更は `test_piece_detail_screen.dart`(共有アイコン追加+ColorSwatchRow への置き換え)、`firing_chart.dart`(duration)、`pubspec.yaml`(share_plus 追加。新規依存はこれのみ)。

### 検証

Windows で保存フロー(ダイアログ→書き込み→SnackBar)、Android で共有シートを実機確認する。ダークテーマ起動時でも出力がライトであること、長い備考でカードが縦に伸びても崩れないこと、画像なしテスピ・オフライン未キャッシュでも書き出せることを確認する。

## 6. アプリアイコン ✅ 実装済み (2026-07-20)

実装結果: 4案からユーザーが「案A 釉掛けタイル」を選択。Pillow で `assets/icon/app_icon.png` (1024px) を生成し、`flutter_launcher_icons` で Android (アダプティブ: 背景=全面絵+前景=透明) / iOS (アルファ除去) / Windows / macOS に適用した。

その後、実機での見え方を比較したいという要望を受けて候補 A/B/D の PNG (`assets/icon/app_icon_{a,b,d}.png`) と切替ツールを追加した。生成スクリプトは `tool/generate_app_icons.py` (functions の venv の Pillow を使用)。**アイコンの切替はプロジェクトルートで `.\tool\set_app_icon.ps1 b` のように実行**すると、選んだ候補を `app_icon.png` にコピーして `flutter_launcher_icons` まで自動で走る。反映にはアプリの再ビルドが必要。最終的に1案へ確定したら、残りの候補PNGは削除してよい。

**第2ラウンド (2026-07-20):** 第1ラウンドの低彩度フラット案は実機で見劣りするとの評価を受け、Play Store の商用アイコン (高彩度グラデーション・光沢・陰影) を参考に E/F/G/H の4案を追加した。第2ラウンドはデザインを SVG (`tool/icons/{e,f,g,h}.svg`) で管理し、`tool/render_app_icons.ps1` が Chrome ヘッドレスで 1024px PNG (`assets/icon/app_icon_{e..h}.png`) にレンダリングする。デザイン修正は SVG を編集 → render → set_app_icon の順。切替は同じく `.\tool\set_app_icon.ps1 e` 等。

**第3ラウンド (2026-07-20):** 第2ラウンドは「色が取っ散らかっている (特にE)」との評価。配色・アイコンデザインのベストプラクティスを調査した結果、(1) 色数は2〜3に絞る (グラデ両端が同一色相なら1色扱い)、(2) 単一モチーフ・明快なシルエット、(3) 60-30-10 (地60%・主色30%・アクセント10%) が要点と判明。これに沿って配色スキーム別 (単色の濃淡 / 類似色 / 補色1点アクセント) に I〜R の10案 (`tool/icons/{i..r}.svg`) を追加した。ブランド色は青磁のティール (#4DEBC8→#0FA0AE) で統一。

**確定 (2026-07-20):** ユーザーが**案M (壺・補色: テラコッタ地×青磁釉)** を選択。`app_icon.png` を M に固定し、Android/iOS/Windows/macOS へ適用済み。

案H (滴と色環) も継続候補として残す方針になり、実機で「ドットの左右非対称」「モチーフが縁に寄りすぎて窮屈」の指摘を受けて修正した。ドットは中心(50,34)・半径24・角度±20/±55/±90度の6点に組み直して左右対称にし、モチーフ全体(滴+波紋+ドット+光沢)を `<g transform="translate(50,54) scale(0.68) translate(-50,-54)">` で中心基準に0.68倍へ縮小した。透過PNGでの実測で余白は上下22.5〜22.9%・左右31.6〜31.7%とほぼ対称かつ十分な余白を確保している(Androidアダプティブアイコンの安全域17%に対して余裕あり)。他候補(A/B/D/E〜G/I〜R)の SVG/PNG もリポジトリに残置し、`tool/set_app_icon.ps1 <案>` でいつでも再比較できる。

### 現状

Android / iOS / macOS / Windows のいずれも `flutter create` が生成したデフォルトアイコンのままである。`flutter_launcher_icons` は未導入で、`assets/` フォルダ自体が存在しない。

### 方針と手順

元絵はユーザーの選択により Claude がデザイン案を作る。手順は次の通り。

1. 釉薬・テスピをモチーフにしたフラットデザインのアイコン案を数案作り、HTML プレビュー(Artifact)でユーザーに提示して1案選んでもらう。
2. 選ばれた案を 1024×1024 の PNG にする。生成方法は実装時に環境を見て選ぶ: Flutter の CustomPainter として描き `flutter test` 内でキャプチャしてファイルに書き出す方法(新規依存なし)か、Python + Pillow が使える環境ならそちらでもよい。成果物は `assets/icon/app_icon.png` に置く(pubspec の assets 宣言は不要。ビルドに含める必要はなくアイコン生成の入力に使うだけ)。
3. `flutter_launcher_icons` を dev_dependencies に追加し、pubspec に設定を書いて Android / iOS / Windows / macOS のアイコンを一括生成する。Android は adaptive icon(背景色 + 前景画像)に対応させるため、前景用に余白を持たせた PNG も用意する(adaptive icon は表示時に中央約66%しか安全に見えないため、通常アイコンと前景画像は別ファイルにする)。
