# glaze_manager 仕様書

陶芸用の釉薬（うわぐすり）レシピ管理アプリケーション。
釉薬の調合情報と焼成結果（テストピース）を関連付けて管理し、オフライン環境でも利用できることを目的とする。
個人利用を想定。

---

## 1. 動作環境・技術スタック

* **ターゲットプラットフォーム:** Windows / macOS / Android
* **オフライン対応:** 必須。オフライン時にもデータの閲覧・編集が可能で、オンライン復帰時に自動同期される。保存操作は楽観的に即完了し、書き込み失敗時は SnackBar で通知する。
* **技術スタック:**
    * クライアント: **Flutter (Dart)** — SDK `^3.9.2`
    * バックエンド: **Firebase** (Authentication / Cloud Firestore / Cloud Storage / Cloud Functions)
    * 状態管理: **Riverpod 2.x** (`flutter_riverpod ^2.6.1`)
* **コスト要件:**
    * Firebase **Blaze プラン**で運用（Cloud Functions に必要）。
    * 個人利用規模では無料枠の範囲に収まる想定。

## 2. Firebase サービス構成

### Authentication（認証）
ユーザー管理。全データをユーザー ID に紐付ける。

* **認証方式:** Google アカウント / メール+パスワード / 匿名サインイン / 引き継ぎコード
* **匿名サインイン:** 警告ダイアログ付きで利用可能。匿名→ Google / メールへの `linkWithCredential` によるアカウントリンク（uid 維持）に対応。
* **引き継ぎコード:** Cloud Functions が12桁のワンタイムコードを発行。SHA-256 ハッシュを `transfer_codes` コレクション（トップレベル）に保存。有効期限なし・1回使用・再発行で旧コード無効。新端末でコード入力→カスタムトークン発行→旧アカウントとしてサインイン。
* **Windows の Google サインイン:** `desktop_webview_auth` 経由（`cloud_functions` プラグインが Windows 非対応のため、callable は HTTPS 直叩き）。

### Cloud Firestore（データベース）
メインデータベース。`persistenceEnabled: true` によるオフライン永続化。

すべてのユーザーデータは `users/{uid}/` 配下のサブコレクションに格納（ユーザー間共有なし）。

| コレクション | 内容 | 主な格納データ |
|---|---|---|
| `materials` | 原料マスター | 材料名、カテゴリ（母剤/添加剤/顔料）、化学成分比（SiO₂, Al₂O₃ 等の Map） |
| `glazes` | 釉薬レシピ | 釉薬名、調合（materials 参照 ID と重量 (g) の Map）、タグ（配列）、`parentGlazeId`（派生元の釉薬）、`parentSnapshot`（複製した時点の派生元の調合の写し） |
| `test_pieces` | テストピース（焼成結果） | 釉薬 ID、追加釉薬 ID 配列、素地土 ID、`firingId`（焼成回）、焼成プロファイル ID と焼成雰囲気 ID（焼成回を参照しない記録だけが使う）、画像パス、サムネイル URL、色味データ（CIELAB 代表色配列）、`snapshot`（記録時の調合と素地土名の写し）、`rating`（評価 1〜5）、`label`（実物に書いた番号）、`relatedGlazeIds`（検索用非正規化フィールド） |
| `clays` | 素地土 | 名前 |
| `firing_profiles` | 焼成プロファイル | 名前、温度曲線データ（チャート表示用）、還元開始/終了温度 |
| `firing_atmospheres` | 焼成雰囲気 | 名前（酸化・還元等） |
| `firings` | 焼成回（窯を焚いた 1 回） | 焼成日（その日の正午の Timestamp）、窯名、焼成プロファイル ID とその時点の写し（名前・温度曲線・還元の有無と温度）、焼成雰囲気 ID とその時点の名前・種類、最高温度、コーン、所感 |
| `tags` | タグ | タグ名（ドキュメント ID = タグ名） |
| `view_history` | 閲覧履歴 | テストピース ID、閲覧日時 |
| `transfer_codes`（トップレベル） | 引き継ぎコード | コードの SHA-256 ハッシュ（= doc ID）、UID、使用済みフラグ |

### Cloud Storage（ストレージ）
テストピース画像の保存。

* **パス形式:** `users/{uid}/test_pieces/images/{docId}/{uuid}.jpg`（新形式）。旧形式（フォルダなし）も互換読み取り対応。
* 一覧表示ではサムネイル（200px）を優先使用（`thumbnailUrl ?? imageUrl`）。原寸画像は詳細画面のみ。

### Cloud Functions（Python 3.13, us-central1）
3モジュール構成: `main.py`（エントリ）/ `image_pipeline.py` / `transfer_codes.py`

* **`process_uploaded_image`**（Storage finalize トリガ）: サムネイル 200px 生成 → K-Means + 凝集マージによる CIELAB 色解析 → Firestore ドキュメントへの `imageUrl` / `thumbnailUrl` / `colorData` 書き戻し → 旧世代ファイル削除。パスの docId からドキュメントを直接解決（旧形式は imagePath クエリでフォールバック）。`colorData` はドキュメントの現在値が空のときのみ書き込む（ユーザーがスポイトで手動登録した色を上書きしない。トランザクションで判定）。同じトランザクションで、ドキュメントの `imagePath` と処理中のファイルのパスを照合する。食い違えば画像が差し替えられた後に届いた古い処理なので、ドキュメントを更新せず、処理中の画像とそのサムネイルを削除する。旧世代ファイルの削除は、処理中の画像より作成時刻が古い画像と、残した画像に対応しないサムネイルに限る（後から届いた新しい画像を消さない）。
* **`issue_transfer_code`** / **`redeem_transfer_code`**（callable, HTTPS 直叩き）: 引き継ぎコードの発行・引き換え。

### セキュリティルール
`firestore.rules` / `storage.rules` でリポジトリ管理。`users/{uid}/**` は `request.auth.uid == uid` のみ読み書き可。`rules_test/`（Node + Firebase Emulator）で検証。

## 3. UI/UX 設計

### ナビゲーション
画面下部のタブバー（Bottom Navigation Bar）による 5 タブ構成:
1. **テストピース**（ホーム）
2. **検索**
3. **釉薬**
4. **原料**
5. **設定**

F5 キーで現在のタブをリフレッシュ可能。UI 文言は日本語。

タブは増やさない。焼成回の一覧は、テストピースタブの AppBar のボタン（炎のアイコン）から開く。

### 共通 UI パターン
* **未保存確認:** 全編集画面で `UnsavedChangesPopScope` による離脱確認ダイアログ。
* **保存操作:** 楽観的 pop（await せず即画面遷移、失敗時 SnackBar 通知）。
* **削除確認:** 参照件数の警告表示付き（「この原料は◯件の釉薬で使用中です」等。焼成回を含む）。
* **同じ情報は同じ部品で:** テストピースの写真は `TestPieceImage`、評価は `RatingStars`、調合は `RecipeTable` / `RecipeDiffTable`、釉薬名・素地土名・焼成の情報は `lib/utils/test_piece_display.dart` の解決関数を、どの画面でも使う。
* **AppBar アクション:** `CommonAppBarActions` で保存ボタン・削除ボタンを統一。

## 4. 主要機能要件（タブ別）

### 4.1. テストピース（ホームタブ）
* ユーザーが追加したテストピースをギャラリー形式（グリッド）で一覧表示。列数は設定から変更可能。
* カードにテストピース画像（サムネイル優先）、釉薬名、素地土名、焼成雰囲気、焼成プロファイルを表示。評価があれば画像の右上に「★4」のように重ねる。アップロード待ちの写真は端末内の画像を表示し、左上に印を付ける（§5）。
* **グループ表示:** AppBar のメニューからグループキー（なし / 素地土 / 焼成雰囲気 / 焼成プロファイル / 焼成回 / 色味 / 評価）を選択でき、セクションヘッダ付きグリッドで表示（`SectionedTestPieceGrid`、CustomScrollView + SliverGrid で遅延ビルド）。選択は設定として永続化（デフォルト「なし」）。
    * 色味は CIELCh ベースの色相バケツ分類（赤/黄/緑/青/紫/茶/白/グレー/黒 + 色データなし。`lib/utils/test_piece_grouping.dart`、閾値は定数化）。代表色は `significantColors` の中で percentage 最大。
    * 素地土等の未設定は「未設定」、マスタ欠落は「不明」グループ（末尾）。
    * 焼成回は ID で束ね、焼成日の新しい順に並べる。末尾に「焼成回なし」「不明」。見出しをタップすると焼成回の詳細を開く。
    * 評価は ★5 から ★1、末尾に「未評価」。
* **評価と番号:** 評価は星 1〜5（未評価は星なし。同じ星をもう一度タップすると取り消す）。番号は実物に書いた番号を入れる自由入力の任意欄で、重複を許す。
* **焼成回:** 窯を焚いた 1 回を表す。焼成日（必須）、窯、焼成雰囲気、焼成プロファイル、最高温度、コーン、所感を一度入力し、同じ窯で焼いたテストピースが参照する。
    * 一覧: 焼成日の新しい順。枚数と、写真のまだないテストピースの枚数（写真待ち）を表示。
    * 詳細: 焼成の情報、プロファイルのチャート、写真待ちのテストピース、この焼成回のテストピースのグリッド。「テストピースを追加」で、焼成回を引き継いだ編集画面を開く。
    * テストピースの編集画面で焼成回を選ぶと、テストピースごとの焼成雰囲気・焼成プロファイルの選択は隠れ、焼成回の値を表示する。その場で焼成回を新規作成することもできる。
    * 焼成回を削除しても、参照していたテストピースの `firingId` は残り、焼成の情報は「不明」と表示される。
* **登録の入口と連続登録:**
    * 一覧の右下のボタン、釉薬の詳細（釉薬を引き継ぐ）、焼成回の詳細（焼成回を引き継ぐ）から編集画面を開ける。
    * 新規作成では「保存して次を登録」で、釉薬・追加釉薬・素地土・焼成回（なければ焼成雰囲気と焼成プロファイル）を引き継いだ次の編集画面へ進む。番号は末尾の数字を 1 増やして提案する（`1108-09` → `1108-10`。`lib/utils/label_increment.dart`）。写真・色・評価・備考は引き継がない。
    * 「複数の写真を選んで連続登録」で写真をまとめて選び、1 枚ずつ切り抜いて連続登録できる。残りの写真があるまま閉じるときは確認する。
    * 写真は任意。窯入れ前に写真なしで登録し、焼成後に写真を付ける使い方ができる。
    * Android では写真の取得元にカメラを選べる（Windows / macOS はファイル選択のみ）。撮影中にアプリが破棄された場合は、次の起動時に `retrieveLostData` で写真を回収して編集画面を開く。
* **比較:** グリッドのカードを長押しすると選択が始まり、2〜4 枚を選んで AppBar の「比較」から比較の画面（`TestPieceCompareScreen`）を開く。ホームタブと焼成回の詳細で使える。写真と各項目を横に並べ、記録のある列どうしで値が違う行を塗る。値のない項目は「—」と表示し、「同じ」とは扱わない。調合は `RecipeDiffTable` で原料ごとに重量と割合を並べ、合計に対する割合が違う行を塗る。
* **詳細画面:**
    * 全画面画像表示（タップで拡大、ズーム操作可能）
    * スポイト検索: スポイト専用画面（`ColorPickScreen`）で画像から色を選び、その色で検索画面へ遷移
    * 色見本: 代表色（CIELAB スウォッチ、`ColorSwatchRow`）を表示。タップでその色を検索。表示する色は `significantColors`（`lib/models/lab_color.dart`）で決める。手動登録の色（percentage が 0）は常に表示し、自動解析の色は面積 5 % を超えるものだけを表示する
    * 調合: 記録時の写し（§5）を表示する。釉薬の現在の調合と違う場合はその旨を表示し、「現在の調合に更新」で写しを取り直せる。釉薬が削除されていても、写しがあれば釉薬名と調合を表示する
    * 評価、番号、焼成回（タップで焼成回の詳細）を表示
    * **共有:** AppBar の共有アイコンから共有プレビュー画面（`TestPieceShareScreen`）へ。写真・評価・色見本・調合・追加釉薬・素地土・焼成雰囲気・焼成チャート・備考を論理幅800pxのカードに合成し、RepaintBoundary キャプチャ（pixelRatio 2.5）で PNG 化。配色は常にライトテーマ。Android/iOS は share_plus の共有シート、Windows/macOS/Linux は保存ダイアログ+自前書き込み（`lib/utils/png_exporter.dart`）
* **スポイト専用画面（`lib/screens/color_pick_screen.dart`）:**
    * 画像を一度だけデコードしピクセルバッファから直接サンプリング（画面のラスタライズは行わない）
    * マーカー周辺のルーペ＋選択色を常時表示。ピンチ/ホイールでズーム可能
    * タッチ: 1本指スワイプでマーカーを相対移動（タップ位置へはジャンプしない）、「決定」で確定。マウス: ホバー位置がマーカー、クリックで確定、ドラッグでパン
    * 詳細画面からは single モード（1色確定で閉じる）、編集画面からは multi モード（連続追加し「完了」で反映）。multi では登録済みの色を参照表示し、重複チェックできる
* **編集画面の色登録:** スポイト（multi モード）でのみ手動追加可能。新画像選択時は色リストをクリアする（colorData の契約は §5 参照）

### 4.2. 検索
複合条件による高度な検索機能。フィルタロジックは純関数 `filterTestPieces`（`lib/services/test_piece_search.dart`）として抽出済み。

* **テキスト検索:** 釉薬名・タグ・原料名・素地土名・焼成雰囲気・焼成プロファイル・番号・窯名・焼成日を検索。スペース区切りで AND 検索、`-語` で除外検索。原料名マッチは釉薬名マッチより後ろにソート。釉薬が削除されていても、調合の写しがあれば釉薬名と原料名で見つかる。
* **色検索:** カラーピッカー（色相環型 `HueRingPicker`）またはスポイトで色を選択。色差（CIE76 ΔE）の閾値をスライダーで調整。判定に使う色は表示と同じ `significantColors`（面積 5 % 以下の自動解析の色は外す）。
* **評価での絞り込み:** 検索バーの星のボタンから「★N 以上」を選ぶ（未評価は外れる）。
* **並び替え:** 結果ヘッダのソートメニューで 関連度順 / 作成が新しい順 / 古い順 / 色が近い順（色検索時のみ表示）/ 評価が高い順（未評価は末尾）を切替（`TestPieceSortOrder`）。デフォルトは色検索中「色が近い順」、それ以外「関連度順」。ユーザーの明示選択は条件変更後も維持し、無効な組み合わせは関連度順にフォールバック。
* **タグ検索:** 登録済みタグから選択して AND 絞り込み。釉薬が削除されているテストピースは外れる。
* 検索条件はチップ表示（除外語は除外アイコン付き）、個別に削除可能。
* 「最近見たテストピース」セクション付き。

### 4.3. 釉薬
* 釉薬レシピの管理（CRUD）。調合の量はすべて重量 (g) で、外割・内割の区別は設けない。
* **詳細画面:** 調合表（原料名と配合量 (g)）、関連テストピースの一覧表示。関連テストピースの見出しの横から、この釉薬を引き継いでテストピースを追加できる。
* **複製と派生:** 詳細画面の「複製して新規作成」で、名前・タグ・調合を写した新しい釉薬を作る。複製した釉薬は、派生元の ID と、複製した時点の派生元の調合の写しを持つ。詳細画面に、派生元（現存すればリンク）、派生元からの変更（`RecipeDiffTable`。違いのある原料だけ）、この釉薬から派生した釉薬の一覧を表示する。
* **調合の編集時の確認:** 調合を変えて保存するとき、この釉薬を写しに持つテストピースがあれば、記録の扱いを尋ねる（キャンセル / 記録はそのまま / 記録も直す）。「記録も直す」は、該当するテストピースの写しのうちこの釉薬の部分を新しい調合に置き換える（誤記の修正用）。名前だけの変更では尋ねない。
* **タグ入力:** 半角・全角スペース、カンマ、読点、Enter、候補の選択で確定する。
* **調合計算:** 総量⇔各原料の双方向換算（`mixing_calculator_screen.dart`）。
* **Excel 一括インポート:** 2 段階処理（パース→プレビューダイアログで件数・スキップ・新規原料を確認→確定）。ヘッダー検証（末尾から3列目=「顔料」、末尾=「備考」）、重複名スキップ、新規原料の自動作成。

### 4.4. 原料
* 釉薬調合に使用する原料の管理（CRUD）。
* カテゴリ区分: 母剤 / 添加剤 / 顔料。
* 化学成分比の登録（ゼーゲル式計算の基礎データ）。
* 詳細画面: この原料を使用している釉薬の一覧。

### 4.5. 設定
* **表示設定:** グリッドの列数変更。
* **焼成プロファイル管理:** 焼成パターンの登録・編集（温度曲線チャートプレビュー付き）。
* **焼成雰囲気管理:** 酸化・還元などの区分管理。
* **素地土管理:** 使用する土の種類の管理。
* **データの書き出し:** 全データを 1 つの ZIP ファイルに書き出す（`lib/services/data_exporter.dart`）。中身は `data.json`（全コレクション。Timestamp は ISO 8601 の UTC 文字列）、`glaze_manager.xlsx`（釉薬・テストピース・原料・焼成回の 4 シート。先頭の「釉薬」シートは Excel 一括インポートがそのまま読める形）、`images/{テストピースID}.jpg`（原寸の写真）。取得できなかった写真は `missingImages` と `missing_images.txt` に記録し、完了の通知で枚数を知らせる。Android は共有シート、Windows / macOS は保存ダイアログで渡す。読み戻し（復元）の機能はない。
* **アカウント:** サインアウト、匿名アカウントのリンク（Google / メール）、引き継ぎコードの発行。

## 5. データフロー上の不変条件

### テストピース保存フロー
1. 新規時は `createTestPieceId()` で ID を先に発行
2. 画像パスを `users/{uid}/test_pieces/images/{docId}/{uuid}.jpg` に確定
3. 新しい画像があれば、`UploadQueue.enqueue` で端末内（アプリケーションサポートの `pending_uploads/{docId}/`）に画像とアップロード待ちの情報を保存する。端末内の書き込みなので、これは待つ
4. **間に非同期の切れ目を挟まずに** Firestore 書き込み（新規: `setTestPiece`、更新: `updateTestPieceFields`）の Future を発火し、UI は即 pop（連続登録なら次の編集画面に置き換える）。失敗は SnackBar で通知
5. `UploadQueue.processAll` が、文書の書き込みがサーバーに届いたことを確かめてから画像をアップロードする
6. Cloud Functions がアップロード完了後に `imageUrl` / `thumbnailUrl` / `colorData` を書き戻す

**アップロード待ちの契約:**

* 選んだ画像は、アップロードが成功するまで端末内に残す。アプリを閉じても失われず、起動時・通信の回復時・アプリが前面に戻ったとき・`enqueue` の直後に送り直す。通信できないあいだは 60 秒ごと、文書の同期待ちのあいだは 20 秒ごとに試し直す。
* 送る前に、テストピースの文書を `Source.server` で読む。この読み取りは成功しても端末の未送信の書き込みを重ねて返すので、`metadata.hasPendingWrites` が true のあいだは送らない。分岐は 5 つ: 読めない → 打ち切る / 文書がない → 待ちを捨てる / 未送信の書き込みがある → 残して次へ / `imagePath` が違う → 待ちを捨てる / 一致 → 送る。Functions は文書の `imagePath` と一致しない画像を削除するので、この順序を崩すと新しい画像が消える。
* 待ちは 1 枚のテストピースにつき 1 つ。送信の完了と失敗の記録は、現在の待ちが同じ `storagePath` のときだけ反映する（送信中に別の画像へ差し替えられた場合に、新しい待ちを消さないため）。
* 待ちは利用者の ID を持つ。現在の利用者のものだけを送り、別の利用者の待ちは残す。
* アップロード待ちの写真は、一覧でも詳細でも端末内の画像を表示し、印を付ける（`TestPieceImage`）。
* `UploadQueue` のコンストラクタはプラグインにも認証にも触れない。待ちの読み込みは `MainTabScreen` が `load()` で行う。

**フィールドの書き手:** テストピースの `imageUrl` と `thumbnailUrl` は Cloud Functions だけが書く。クライアントは更新時にこれらを送らない（`TestPiece.toUpdateFields`）。全フィールドを送り直すと、編集画面を開いたあとに Functions が書き戻した値を古い値で上書きしてしまうためである。`imagePath` は新しい画像を選んだときだけ、`colorData` は色を編集したときだけ、`snapshot` は取り直したときだけ送る。`createdAt` は作成時にだけ書く。

**colorData の契約:** 新画像選択時にクライアントは `colorData` をクリアする。保存時は、色を編集したとき（スポイトで足した、削除した）または新しい画像を選んだときだけ、編集画面の現在の色リストを渡す。Functions は書き戻し時にドキュメントの `colorData` が**非空なら colorData の書き込みをスキップ**する（トランザクションで判定）。空なら解析結果を書き込む。これによりスポイトで手動追加した色が自動解析に上書きされない。

**調合の写しの契約:**

* テストピースは、記録した時点の調合（主たる釉薬と追加釉薬）と素地土名の写しを `snapshot` に持つ。表示・検索・共有・比較は写しを使う。釉薬を編集・削除しても、過去の記録は変わらない。
* 量は常に写しの値を使う。名前（釉薬名・原料名・素地土名）は、元の文書が残っていれば現在の名前を、削除されていれば写しの名前を表示する（改名は過去の表示にも反映される）。
* 写しを取るのは、新規作成のときと、編集で主たる釉薬・追加釉薬・素地土のいずれかを変えたときである。備考や評価だけの編集では写しは変わらない。
* `source` は写しの出どころを表す。`saved`（登録・編集時）、`backfilled`（写しのなかった既存データに、起動時に現在の調合から一度だけ埋めたもの。当時の調合とは限らないので詳細画面に注記を出す）、`corrected`（釉薬の誤記の修正を反映したもの）。
* 追加釉薬の写しは、`additionalGlazeIds` と要素数が一致するとは限らない。対応は添字ではなく `glazeId` で取る。

**焼成の情報の解決:** テストピースの焼成の情報は `resolveFiring`（`lib/utils/test_piece_display.dart`）だけで決める。`firingId` があれば焼成回を正とし（雰囲気とプロファイルの名前は現存すれば現在の値、なければ焼成回の写し。温度曲線と還元の値は常に焼成回の写し）、焼成回が見つからなければ「不明」とする。`firingId` がなければ、テストピースの `firingAtmosphereId` と `firingProfileId` から現在の値を引く。新しい記録で両方を持つことはしない。

### その他の保存フロー
釉薬・原料・素地土・焼成プロファイル・焼成雰囲気・焼成回の保存はすべて楽観的 pop。書き込み Future を await せず即画面遷移し、失敗時は SnackBar で通知。
