# 実装計画書 — 試験ノート化

本書は `docs/価値向上方針.md` の「第一のまとまり」を、実装できる水準まで具体化した計画書である。実装を担当するモデル（またはセッション）は、まず `docs/spec.md` で現在の仕様を、次に `docs/価値向上方針.md` の第 5 章（判断の原則）と第 6 章（目指す記録の姿）で狙いを把握したうえで本書を読むこと。迷ったときは、個々の指示よりも方針文書の原則に立ち返って判断してよい。

本書中の行番号は 2026-11-10 時点のコード（コミット df628ee）に対するものである。実装が進むとずれるので、「何を探すか」の手がかりとして扱うこと。行番号を付けていない箇所は、メソッド名や文言で探すこと。

## 0. 全体像

### 0.1 何を作るか

テストピースの記録を「ラベルの付いた写真」から「試験の結果」へ作り直す。具体的には次の 10 項目である。章の順は実装の順でもある。

| 章 | 項目 | 主な狙い |
|---|---|---|
| 1 | 小さな修正と表記の統一 | 後の章の足場。既知の不整合の解消 |
| 2 | テストピースの更新を変更分だけにする | Cloud Functions が書いた値を古い値で上書きする不具合の解消 |
| 3 | 調合の写し | 釉薬を編集・削除しても、過去の記録が変わらないようにする |
| 4 | 釉薬の複製と派生 | 改良を上書きではなく派生として残す |
| 5 | 評価とピースの番号 | 判断と、実物との照合の手がかりを残す |
| 6 | 焼成回 | 焼いた日・条件・実績を一度の入力で複数のテストピースに持たせる |
| 7 | 比較表示 | 2〜4 枚を並べて違いを見る |
| 8 | アップロード待ちの永続化 | オフラインで選んだ写真が、アプリを閉じても失われないようにする |
| 9 | 入力の作り直し | 連続登録、カメラ撮影、複数写真の一括選択、文脈を引き継ぐ入口 |
| 10 | 全データの書き出し | 記録をアプリの外へ取り出せるようにする |

第 11 章でドキュメントを更新し、第 12 章で全体を検証する。

### 0.2 利用者に確認済みの判断

次の事項は利用者に確認して確定している。実装中に再検討しなくてよい。

| 事項 | 決定 |
|---|---|
| 進め方 | 本書の 10 項目を一本の計画として一度に実装する。段階的なリリースはしない |
| 調合の量 | すべて重量（g）。外割・内割の区別は設けない |
| 評価 | 星 1〜5。未評価は星なし |
| ピースの番号 | 自由入力の任意欄。重複を許す。利用者の付け方は「日付＋番号」 |
| 焼成前の登録 | 窯入れ前に登録する使い方と、焼成後に写真から登録する使い方の両方を同じ画面で扱う |
| 再焼成 | ほぼ行わない。テストピースが参照する焼成回は一つ |
| 焼成回の一覧の場所 | テストピースタブの AppBar のボタンから開く。画面下部の 5 タブは変えない |

本書の中で筆者が決めた事項は、各章に理由とともに書いてある。利用者の UI 方針（`同じ情報は常に同じ UI に載せる`、装飾を足さない、ダイアログは不可逆な操作の確認に限る）に沿って決めている。

### 0.3 データモデルの変更の一覧

すべて任意フィールドの追加と、新しいコレクション一つである。既存の文書はそのまま読める必要がある。新しいフィールドの読み取りは、欠損と数値の `int`/`double` の違いに耐えるように書くこと（AGENTS.md の方針）。

`test_pieces` の文書に足すフィールドは、`snapshot`（調合と素地土名の写し。第 3 章）、`rating`（評価。第 5 章）、`label`（ピースの番号。第 5 章）、`firingId`（焼成回への参照。第 6 章）である。`glazes` の文書には `parentGlazeId` と `parentSnapshot`（第 4 章）を足す。新しいコレクションは `users/{uid}/firings`（第 6 章）である。

`firestore.rules` は `users/{userId}/{document=**}` を本人に許可しているので、新しいコレクションを足してもルールとルールテストの変更は要らない。クエリはすべて全件購読をクライアントで絞る既存の流儀に従うので、`firestore.indexes.json` の変更も要らない。

### 0.4 共通の注意

**モックの再生成。** 画面テストの大半は `test/screens/main_tab_screen_test.mocks.dart` の `MockFirestoreService` を共用している。`FirestoreService` や `StorageService` にメソッドを足したら `dart run build_runner build --delete-conflicting-outputs` で再生成すること。`MockFirestoreService` はスタブしていないメソッドを呼ぶと例外を投げる。第 6 章で多くの画面が焼成回の一覧を購読するようになるので、既存の画面テストの setUp に `getFirings()` のスタブを足す必要がある（`test/screens/main_tab_screen_test.dart` の setUp にある `getFiringProfiles` などのスタブが手本）。

**楽観的な画面遷移。** 編集画面の保存は、Firestore への書き込みを待たずに画面を閉じ、失敗は SnackBar で知らせる。新しく作る編集画面も同じにする。SnackBar を出す `ScaffoldMessenger` は、画面を閉じる前に取得しておく（`lib/screens/firing_profile_edit_screen.dart` の保存処理が手本）。

**コミット。** 章ごとにコミットを分ける。各章の終わりで `dart format`、`flutter analyze`、`flutter test` を通すこと。

**デプロイ。** 第 8 章で Cloud Functions を変更する。デプロイは利用者の明示的な指示があるまで行わない。

### 1.2 タグ入力の区切り文字による確定を直す

**現状と問題。** 釉薬の編集画面のタグ入力は、ラベルで「スペース or カンマで確定」と案内している（`glaze_edit_screen.dart` 378 行）。しかし区切り文字を監視するリスナー `_onTagInputChanged`（84-96 行）は `_tagInputController`（27 行）に付いており、このコントローラはどの入力欄にも渡されていない。実際の入力欄は `Autocomplete` が内部で作る `fieldTextEditingController` を使っている（429 行）。このため区切り文字による確定は働かず、確定の経路は Enter（`onSubmitted`、437-447 行）と候補の選択（`onSelected`、409-418 行）だけになっている。`onSelected` が呼ぶ `_tagInputController.clear()`（416 行）も、実際の入力欄を消していない。

**変更内容。** `_tagInputController` と `_onTagInputChanged` を削除する（27、57、84-96、103、107 行の関連箇所）。`fieldViewBuilder`（419-449 行）で受け取る `fieldTextEditingController` を State のフィールド（たとえば `TextEditingController? _tagFieldController`）に控えておき、入力欄の `onChanged` で区切り文字を調べる。区切り文字は半角スペース、全角スペース、半角カンマ、読点（、）とする。区切り文字を含む入力があったら、区切り文字で分割し、空でない語を `_tags` に足し（重複は足さない）、入力欄を空にし、`_markAsDirty()` を呼ぶ。`onSelected` と `onSubmitted` でも `_tagFieldController` を使って入力欄を空にする。

**テスト。** `test/screens/glaze_edit_screen_test.dart` に、入力欄へ「青磁 還元」と入力するとタグのチップが 2 つできることを確かめるテストを足す。

### 1.4 色の判定から小面積の色を外し、手動の色を見えるようにする

**現状と問題。** 色見本の表示は面積 5 % を超える色だけに絞っている（`lib/widgets/common/color_swatch_row.dart` 22-24 行）。一方、色検索はすべての色との最小距離で判定する（`lib/services/test_piece_search.dart` 149-154 行）。面積 1 % のハイライトや影にも反応するので、白や黒で検索すると無関係なテストピースが混じる。画面に見えていない色で検索に当たる、という食い違いがある。

逆の食い違いもある。スポイトで手動登録した色は `percentage` が 0 で保存される（`LabColor.fromColor` は `percentage: 0` を返す。`lib/models/lab_color.dart`）。色見本の表示条件は `percentage > 5.0` なので、手動で登録した色は詳細画面にも共有画像にも表示されない。検索には当たるのに見えない。

**変更内容。** 「判定と表示に使う色」を一か所で決める関数を `lib/models/lab_color.dart` に足し、表示・検索・グループ化の三者がこれを使う。

```dart
/// 自動解析の色のうち、この面積（%）以下のものは判定と表示から外す。
const double minSignificantColorPercentage = 5.0;

/// 判定と表示に使う色を返す。
/// 手動登録の色（percentage が 0）は常に含める。
/// 自動解析の色は percentage が閾値を超えるものだけを含める。
/// 何も残らない場合は、percentage が最大の 1 色を返す。
List<LabColor> significantColors(List<LabColor>? colorData)
```

`ColorSwatchRow` の 22-24 行の絞り込みをこの関数に置き換える。これで手動の色が見えるようになる。`filterTestPieces` の色検索のループ（149 行）は、`testPiece.colorData!` の代わりに `significantColors(testPiece.colorData)` を回す。グループ化の `representativeColor`（`lib/utils/test_piece_grouping.dart` 145-152 行）は、`significantColors` の結果の中から `percentage` が最大のものを選ぶ（すべて 0 なら先頭。現在の挙動と同じ）。

**エッジケース。** 自動解析の色がすべて 5 % 以下という記録は、最大の 1 色が残る。色データが空または null の記録は、これまで通り色検索から外れ、色味のグループでは「色データなし」に入る。

**テスト。** `test/services/test_piece_search_test.dart` に、面積 2 % の白を持つテストピースが白の検索に当たらないこと、`percentage` が 0 の色は当たることを足す。既存の色検索のテストは `LabColor.fromColor`（`percentage` は 0）で色を作っているので、そのまま通るはずである。`test/utils/test_piece_grouping_test.dart` の `representativeColor` のテストに、小面積の色が代表に選ばれないケースを足す。`ColorSwatchRow` にはテストがないので、手動の色が表示されることを確かめるウィジェットテストを新設する。

## 2. テストピースの更新を変更分だけにする

### 現状と問題

テストピースの写真の URL（`imageUrl`）、サムネイルの URL（`thumbnailUrl`）、自動解析した色（`colorData`）は、Cloud Functions が画像のアップロード後に書き戻す（`functions/image_pipeline.py` 243-258 行）。ところがクライアントは、テストピースを更新するときに全フィールドを送り直す。`UserScopedRepository.updateById` は `collection.doc(id).update(toFirestore(item))` であり（`lib/repositories/user_scoped_repository.dart` 62-67 行）、`TestPiece.toFirestore` は `imageUrl` と `thumbnailUrl` を null のままでも出力する（`lib/models/test_piece.dart` 59-75 行）。編集画面は、画面を開いた時点の値をそのまま送る（`lib/screens/test_piece_edit_screen.dart` 171、173、175 行）。

このため、新規登録の直後に同じテストピースを開いて備考を直す、といった操作をすると、編集画面を開いたあとに Functions が書き戻した URL と色が、画面の持つ古い値（null と空のリスト）で上書きされる。画像のファイルは Storage に残るが、文書からは参照が消え、再び解析が走ることもない。第 9 章で連続登録を入れると、この操作は起きやすくなる。

### 方針

フィールドごとに書き手を一つに決める。`imageUrl` と `thumbnailUrl` は Functions だけが書き、クライアントは更新時に送らない。`colorData` は、利用者が編集画面で色を変えたとき（スポイトで足した、削除した、新しい画像を選んだ）だけ送る。`imagePath` は新しい画像を選んだときだけ送る。`createdAt` は作成時にだけ書く。

新規作成は従来通り文書全体を `set` する。新しい文書には Functions が書いた値がまだないので、上書きの問題は起きない。

### 変更内容

`lib/models/test_piece.dart` に、更新用のフィールドの集合を作るメソッドを足す。

```dart
/// 更新時にクライアントが送るフィールド。
/// imageUrl / thumbnailUrl（Cloud Functions が書く）と createdAt は含めない。
Map<String, dynamic> toUpdateFields({
  required bool includeImagePath,
  required bool includeColorData,
})
```

実装は `toFirestore()` の結果から `imageUrl`、`thumbnailUrl`、`createdAt` を除き、引数が false なら `imagePath`、`colorData` も除く。`relatedGlazeIds` は `toFirestore()` が `glazeId` と `additionalGlazeIds` から導いているので、そのまま含まれる。第 3 章で写しのフィールドが増えたら、同じ流儀で引数を一つ足す。

`lib/repositories/test_piece_repository.dart` に部分更新のメソッドを足す。このクラスには `setById` という固有のメソッドがすでにあるので、同じ並びに置く。

```dart
Future<void> updateFields(String id, Map<String, dynamic> fields) async {
  await collection.doc(id).update(fields);
}
```

`lib/services/firestore_service.dart` のテストピースのメソッド群（114-145 行）に `updateTestPieceFields(String id, Map<String, dynamic> fields)` を足して委譲する。既存の `updateTestPiece`（140-141 行）は、全フィールドの更新を誤って再び使わないように削除する。lib 内の呼び出し元は編集画面の 186 行だけである。

`lib/screens/test_piece_edit_screen.dart` に `bool _colorsDirty = false;` を足し、色が変わる 3 箇所で true にする。新しい画像を選んで色を空にする箇所（`_pickImage` の 117-121 行付近）、色を削除する箇所（646 行付近）、スポイトで足した色を反映する箇所（686 行付近）である。保存処理の更新の分岐（184-186 行）を次のように変える。

```dart
final writeFuture = (widget.testPiece == null)
    ? firestoreService.setTestPiece(docId, testPieceData)
    : firestoreService.updateTestPieceFields(
        docId,
        testPieceData.toUpdateFields(
          includeImagePath: hasNewImage,
          includeColorData: _colorsDirty,
        ),
      );
```

`docs/spec.md` §5 の「colorData の契約」は、「保存時は編集画面の現在の色リストをそのまま渡す」を「色を編集したとき、または新しい画像を選んだときだけ、編集画面の現在の色リストを渡す」に書き換える。Functions 側の契約（空のときだけ解析結果を書く）は変わらない。

### エッジケース

新しい画像を選ぶと色は空になり、`_colorsDirty` が true になるので、空のリストが送られる。Functions は空を見て解析結果を書く。従来と同じ動きである。新しい画像を選び、スポイトで色を足して保存した場合は、その色が送られ、Functions は解析結果を書かない。これも従来と同じである。

既存のテストピースの画像を差し替えた場合、`imageUrl` は古い画像の URL のまま残り、Functions の書き戻しで新しい URL に変わる。その間は古い画像が表示される。第 8 章で、この間は端末内の新しい画像を表示するようになる。

### テスト

`test/models/test_piece_test.dart` に `toUpdateFields` のテストを足す（`imageUrl`、`thumbnailUrl`、`createdAt` が含まれないこと、2 つの引数で `imagePath` と `colorData` の有無が切り替わること、`relatedGlazeIds` が含まれること）。`test/screens/test_piece_edit_screen_test.dart` に、既存のテストピースを開いて備考だけを変えて保存すると、`updateTestPieceFields` が `imageUrl`、`thumbnailUrl`、`colorData` を含まない Map で呼ばれることを確かめるテストを足す。モックを再生成すること。

## 3. 調合の写し

### 現状と問題

テストピースは釉薬の ID を参照するだけで、焼いた時点の調合を自分では持たない（`lib/models/test_piece.dart`）。詳細画面は現在の釉薬を引いて調合表を描く（`lib/screens/test_piece_detail_screen.dart` 329 行の `RecipeTable(recipe: glaze.recipe, materials: materials)`）。共有画像も同じである（`lib/screens/test_piece_share_screen.dart` 240 行）。このため、試験のあとで釉薬の調合を書き換えると、過去のテストピースに表示される調合も黙って変わる。利用者はこの書き換えを「たまに」行っている。

釉薬を削除すると、被害はさらに大きい。詳細画面は主たる釉薬が見つからないと、画面全体を「関連する釉薬データが見つかりません。」に置き換える（117-118 行）。追加釉薬は見つからないものが黙って消える（89-93 行付近の `whereType<Glaze>()`）。検索は釉薬の見つからないテストピースを結果から外す（`lib/services/test_piece_search.dart` 76-78 行）。

### 方針

テストピースに、記録した時点の調合と素地土名を写しとして持たせる。表示・検索・共有は写しを使う。写しがない古い記録は、従来通り現在の釉薬を引く。既存のテストピースには、一度だけ現在の調合から写しを埋める。

名前と量で扱いを分ける。量は写しの値を常に使う。名前（釉薬名、原料名、素地土名）は、元の文書が残っていれば現在の名前を表示し、削除されていれば写しの名前を表示する。改名は誤記の修正であることが多いので、過去の表示にも反映させたい。写しの名前は、元が消えたときの備えである。

### データの形

新しいファイル `lib/models/recipe_snapshot.dart` に 3 つのクラスを置く。

```dart
/// 調合の 1 行。
class RecipeLine {
  final String materialId;
  final String name;      // 記録時の原料名
  final String category;  // 記録時の MaterialCategory.name
  final double amount;    // 重量 (g)
}

/// ある時点の釉薬の調合。
class GlazeSnapshot {
  final String glazeId;
  final String name;
  final String? registeredName;
  final List<RecipeLine> lines;

  /// 現在の釉薬と原料から写しを作る。
  /// 原料が見つからない行は name を '不明な原料'、category を 'base' とする。
  factory GlazeSnapshot.capture(Glaze glaze, Map<String, Material> materialById);
  factory GlazeSnapshot.fromMap(Map<String, dynamic> map);
  Map<String, dynamic> toMap();

  /// 原料 ID → 量。
  Map<String, double> get recipe;

  /// 原料 ID の集合が同じで、すべての量の差が 1e-9 以下なら true。
  bool hasSameRecipeAs(Map<String, double> other);
}

/// テストピースが持つ写しの全体。
class TestPieceSnapshot {
  final GlazeSnapshot? glaze;                 // 主たる釉薬
  final List<GlazeSnapshot> additionalGlazes; // 追加釉薬。対応は glazeId で取る
  final String? clayName;
  final String source;     // 'saved' | 'backfilled' | 'corrected'
  final Timestamp takenAt;
}
```

`source` の意味は次の通りである。`saved` は登録や編集のときに取った写し、`backfilled` は既存データに一度だけ埋めた写し、`corrected` は釉薬の誤記の修正を反映した写し（第 4 章）である。

`additionalGlazes` は、テストピースの `additionalGlazeIds` と要素の数が一致するとは限らない。既存データに埋めるとき、すでに削除されている追加釉薬は写しに入らないからである。追加釉薬の写しを使う箇所は、添字ではなく `glazeId` で対応を取ること。

Firestore の文書では、`test_pieces` の `snapshot` フィールドに次の形で入れる。

```
snapshot: {
  source: 'saved',
  takenAt: <Timestamp>,
  clayName: '信楽白',
  glaze: { glazeId, name, registeredName, lines: [ {materialId, name, category, amount}, ... ] },
  additionalGlazes: [ { ...同じ形... } ]
}
```

`fromMap` は欠損に耐えるように書く。`lines` の `amount` は `(value as num).toDouble()` で読む。`snapshot` が Map でなければ null として扱う。

`lib/models/test_piece.dart` に `final TestPieceSnapshot? snapshot;` を足す。`fromFirestore` は上記の通り寛容に読み、`toFirestore` は `if (snapshot != null) 'snapshot': snapshot!.toMap()` を出力する。第 2 章の `toUpdateFields` に `required bool includeSnapshot` を足し、false なら `snapshot` を除く。

写しを作るには原料の ID からモデルを引く必要があるが、現在あるのは名前だけの `materialNameMapProvider` である（`lib/providers/data_providers.dart` 151-156 行）。同じファイルに `materialMapProvider`（`Provider<Map<String, Material>>`）を、ほかの Map プロバイダと同じ書き方で足す。

### 写しを取る時点

編集画面の保存処理（`_saveTestPiece`、127-222 行）で写しを作る。必要な Map は `ref.read(glazeMapProvider)`、`ref.read(materialMapProvider)`、`ref.read(clayMapProvider)` で得る。

新規作成のときは、選ばれた主たる釉薬、追加釉薬、素地土から写しを作り、`source: 'saved'` で文書に含める。

更新のときは、主たる釉薬の ID、追加釉薬の ID の並び、素地土の ID のいずれかが `widget.testPiece` から変わった場合、または `widget.testPiece.snapshot` が null の場合に限り、写しを作り直して送る（`includeSnapshot: true`）。どれも変わっていなければ送らない。これにより、備考や評価だけを直す編集では写しは変わらない。写真を付ける操作でも変わらない。

### 表示の変更

**調合表の部品。** `RecipeTable`（`lib/widgets/common/recipe_table.dart`、53 行）は `Map<String, double> recipe`（キーは原料 ID）と `List<Material> materials` を受け取り、ID で原料名を引いて、量の多い順に並べる。原料が見つからないと「不明な原料」と表示する（38 行）。ここに写しから作る名前付きコンストラクタを足す。

```dart
/// 写しから調合表を作る。原料が現存すれば現在の名前を、
/// 削除されていれば写しの名前を表示する。
RecipeTable.fromSnapshot({
  Key? key,
  required GlazeSnapshot snapshot,
  required List<Material> materials,
})
```

内部の実装は、両方のコンストラクタが「原料 ID、表示名、量、タップで開く原料（あれば）」の行のリストを作り、同じ描画に渡す形に整理する。列見出し、並び順、行をタップすると原料の詳細を開く挙動は、現在と同じにする。

**テストピースの詳細画面。** `lib/screens/test_piece_detail_screen.dart` の変更は次の通りである。

主たる釉薬が見つからないときに画面全体を置き換える分岐（117-118 行）をなくす。釉薬名は `glaze?.name ?? testPiece.snapshot?.glaze?.name ?? '不明な釉薬'` で決める。`_buildWideLayout`、`_buildNarrowLayout`、`_buildInfoPanel` は現在 `Glaze glaze` を非 null で受け取っているので、null を受けられるように直す。

調合の節（304-331 行）は、`testPiece.snapshot?.glaze` があれば `RecipeTable.fromSnapshot` で描き、なければ従来通り `glaze.recipe` で描く。どちらもなければ節を出さない。「調合計算へ」のボタン（309-325 行）が `MixingCalculatorScreen` に渡す調合と原料名も、写しがあれば写しから作る。

写しと現在の調合が違う場合の表示を足す。`glaze` が現存し、写しがあり、`snapshot.glaze.hasSameRecipeAs(glaze.recipe)` が false のとき、調合表の上に本文と同じ書体で「釉薬の現在の調合とは異なります。」と表示し、その横に「現在の調合に更新」のテキストボタンを置く。ボタンを押すと確認のダイアログ（「このテストピースの調合の記録を、釉薬の現在の調合に置き換えます。元に戻せません。」）を出し、確定したら写しを作り直して `updateTestPieceFields(id, {'snapshot': ...})` で保存する。`source` は `saved` とする。

`source` が `backfilled` の写しには、調合表の下に `bodySmall` の書体で「移行時に、その時点の釉薬の調合から埋めた記録です。」と表示する。当時の調合とは限らないことを利用者が知るためである。

主たる釉薬の `InfoTile`（333-343 行）は、釉薬が現存するときだけタップで釉薬の詳細へ飛ぶ。追加釉薬（344-368 行）は、`additionalGlazeIds` を順に回し、現存すれば現在の名前とリンクを、なければ写しの名前（リンクなし）を、どちらもなければ「不明な釉薬」を表示する。見つからない追加釉薬を黙って消す現在の挙動をやめる。素地土名（369 行付近）は `clay?.name ?? testPiece.snapshot?.clayName ?? '未設定'` とする。

**共有画像。** `lib/screens/test_piece_share_screen.dart` の `_buildCaptureCard`（183-277 行）も同じ規則にする。釉薬名（125-126 行）、調合表（237-242 行）、追加釉薬の名前（195-198 行）、素地土名である。

**カードとリスト。** `TestPieceGrid.buildCard`（`lib/widgets/test_piece_grid.dart` 59-60 行）の釉薬名と素地土名を、現存しなければ写しの名前を使うように直す。検索画面のリスト表示（`lib/screens/search_screen.dart` 809-844 行）と「最近見たテストピース」（704 行付近）は同じ名前解決をその場に書いているので、同様に直す。三か所に同じ解決が散っているので、`lib/utils/test_piece_display.dart` に `String glazeDisplayName(TestPiece, Map<String, Glaze>)` と `String clayDisplayName(TestPiece, Map<String, Clay>)` を置いて共用する。第 6 章で焼成の情報の解決もこのファイルに足す。

**検索。** `filterTestPieces`（`lib/services/test_piece_search.dart`）の変更は次の通りである。釉薬が見つからないテストピースを外す処理（76-78 行）は、写しもない場合に限って外すように変える。検索対象の文字列（85-91 行）の釉薬名は上記の `glazeDisplayName` と同じ規則で決め、タグは釉薬が現存するときだけ含める。原料名（94-97 行）は、写しがあれば写しの各行について「現存すれば現在の原料名、なければ写しの名前」を連結し、写しがなければ従来通り `glaze.recipe.keys` から作る。タグによる絞り込み（130-136 行）は、釉薬が現存しないテストピースを従来通り外す。

### 既存データへの適用

既存のテストピースには、現在の調合から一度だけ写しを埋めて保存する。

計画を立てる純関数を `lib/services/snapshot_backfill.dart` に置く。

```dart
/// 写しを持たないテストピースについて、埋めるべき写しを返す。
/// 主たる釉薬が見つからないテストピースは対象にしない。
Map<String, TestPieceSnapshot> planSnapshotBackfill({
  required List<TestPiece> pieces,
  required Map<String, Glaze> glazeMap,
  required Map<String, Material> materialMap,
  required Map<String, Clay> clayMap,
})
```

返す写しの `source` は `backfilled` とする。追加釉薬のうち見つからないものは写しに含めない。

これを呼ぶプロバイダを `lib/providers/data_providers.dart` に足す。`testPiecesProvider`、`glazesProvider`、`materialsProvider`、`claysProvider` の 4 つすべてが、値を持ち、かつ読み込み中でない（`hasValue && !isLoading`）ときだけ計画を返し、それ以外は空の Map を返す。読み込みの途中で「釉薬が見つからない」と誤って判断しないためである。`hasValue` だけで判定してはならない。Riverpod の `StreamProvider` は、サインインし直したときなどの再購読のあいだ、前の値を保ったまま読み込み中になる。

書き込みは `TestPieceRepository` に `updateFieldsBatch(Map<String, Map<String, dynamic>> fieldsById)` を足して行う。`WriteBatch` に `update` を積み、400 件ごとに区切って commit する。`FirestoreService` に委譲メソッドを足す。

実行するのは `MainTabScreen`（`lib/screens/main_tab_screen.dart`）である。この画面はサインイン済みのときだけ生成される。`initState`（67 行）で `ref.listenManual` を使って上記のプロバイダを監視し（`fireImmediately: true`）、計画が空でなければ書き込みを呼ぶ。書き込みを呼んだテストピースの ID は State の `Set<String>` に控え、同じセッションで二度呼ばないようにする。書き込むとローカルのキャッシュがすぐに更新され、プロバイダが再計算されて計画は空になる。フラグを別に保存する必要はなく、何度起動しても結果は変わらない。

### エッジケース

釉薬が削除済みで写しを埋められないテストピースは、写しなしのまま残る。表示は従来通り「不明な釉薬」になる。

すでに書き換えられた調合は、埋めた写しからは復元できない。利用者が元の記録を見て直したい場合は、釉薬を当時の調合に戻してから、テストピースの詳細画面で「現在の調合に更新」を押す。

写しを持つテストピースの釉薬を選び直して保存すると、写しは新しい釉薬のもので取り直される。

### テスト

`test/models/` に `recipe_snapshot_test.dart` を新設する（`capture`、`fromMap` と `toMap` の往復、整数で保存された量の読み取り、欠損のあるデータ、`hasSameRecipeAs`）。`test/models/test_piece_test.dart` に写しの往復と、写しのない文書が読めることを足す。`test/services/` に `snapshot_backfill_test.dart` を新設する（写しのないテストピースだけが対象になること、釉薬が見つからないものは対象外であること）。`test/services/test_piece_search_test.dart` に、釉薬が削除されていても写しがあれば釉薬名と原料名で見つかることを足す。`test/screens/test_piece_detail_screen_test.dart` に、写しの調合が表示されること、現在の調合と違うときに注記が出ること、釉薬が削除されていても画面が表示されることを足す。

## 4. 釉薬の複製と派生

### 現状と問題

釉薬の調合を改良したとき、利用者には二つの道しかない。元の釉薬を上書きするか、新規作成の画面で調合を一から入力し直すかである。手間の少ない上書きが選ばれやすく、どの釉薬がどの釉薬の改良であるかは名前以外に残らない。釉薬に複製の操作はなく、派生元を表すフィールドもない（`lib/models/glaze.dart`）。

### 方針

釉薬の詳細画面に「複製して新規作成」を足す。複製して作った釉薬には、複製元の ID と、複製した時点の複製元の調合を記録する。複製元は後で編集されうるので、ID だけでは派生時との差を再現できないからである。釉薬の詳細画面に、派生元、派生元からの変更点、その釉薬から派生した釉薬の一覧を表示する。

また、テストピースが紐づいている釉薬の調合を編集して保存するとき、記録済みの写しをどうするかを尋ねる。

### データの形

`lib/models/glaze.dart` に `final String? parentGlazeId;` と `final GlazeSnapshot? parentSnapshot;` を足す。`fromFirestore` は欠損に耐えるように読み、`toFirestore` は null でないときだけ出力する。

なお、釉薬の保存は現在も全フィールドの更新である（`_saveGlaze` が `Glaze` を組み立てて `updateGlaze` を呼ぶ）。釉薬には Cloud Functions が書くフィールドがないので、テストピースのような上書きの問題はない。新しい 2 つのフィールドは null のとき出力しないので、編集で保存しても文書に入っている値は消えない（更新は `update` であり、出力しなかったフィールドには触れない）。それでも、編集画面で `Glaze` を組み立てるときには `widget.glaze` の `parentGlazeId` と `parentSnapshot` を引き継いでおくこと。組み立てたモデルと文書の内容が食い違わないようにするためである。

### 複製の操作

`lib/screens/glaze_edit_screen.dart` のコンストラクタ（13-20 行）に `final Glaze? sourceGlaze;`（複製元）を足す。`glaze` が null で `sourceGlaze` が非 null のとき、複製として扱う。

`initState`（40-74 行）で、複製のときは次のように初期化する。釉薬名は複製元の名前を入れる。登録名と備考は空にする。タグは複製元のものを写す。調合の行は複製元の `recipe` から、編集時と同じ処理（59-73 行）で作る。`_isDirty` は最初から true にする。入力せずに戻ろうとしたときに、未保存の確認が出るようにするためである。AppBar のタイトル（242 行）は「釉薬の複製」とする。

保存処理（`_saveGlaze`、115-168 行）で `Glaze` を組み立てるとき（131-141 行）、複製の場合は `parentGlazeId: widget.sourceGlaze!.id` と `parentSnapshot: GlazeSnapshot.capture(widget.sourceGlaze!, materialMap)` を入れる。編集の場合は `widget.glaze` の値を引き継ぐ。

`lib/screens/glaze_detail_screen.dart` の AppBar（50-62 行）で、編集ボタンの前に `IconButton`（アイコンは `Icons.copy_outlined`、ツールチップは「複製して新規作成」）を足し、`GlazeEditScreen(sourceGlaze: glaze)` へ遷移する。

### 詳細画面の表示

`glaze_detail_screen.dart` の `_buildContent`（70-134 行）に 3 つを足す。

派生元。`parentGlazeId` があるとき、登録名やタグの並びに `InfoTile(label: '派生元', ...)` を足す。値は、派生元が現存すれば現在の名前（タップで派生元の詳細へ）、なければ `parentSnapshot` の名前（リンクなし）とする。

派生元からの変更。`parentSnapshot` があるとき、調合表の下に「派生元からの変更」の見出しと、第 7 章で作る `RecipeDiffTable` を 2 列（派生元、この釉薬）で置く。違いのある原料だけを表示する。違いが一つもなければ「派生元と同じ調合です。」と表示する。第 7 章より先に本章を実装する場合は、この表示だけ第 7 章のあとで足せばよい。

派生した釉薬。`glazesProvider` から `parentGlazeId == glaze.id` の釉薬を拾い、一つ以上あれば「派生した釉薬」の見出しと名前の一覧（タップで詳細へ）を置く。

### 編集時の確認

`_saveGlaze` の検証のあと、書き込みの前に、次の条件をすべて満たすときに限りダイアログを出す。編集である（`widget.glaze != null`）。調合が `widget.glaze!.recipe` から変わっている（原料 ID の集合か量が違う）。この釉薬を主たる釉薬または追加釉薬として写しに持つテストピースが 1 件以上ある。

件数は、削除確認（`_confirmDelete`、170-230 行）と同じく `await ref.read(testPiecesProvider.future)` で全件を取り、`snapshot` の中の `glazeId` が一致するものを数える。

ダイアログの文言と選択肢は次の通りとする。

- 題: 「テストピースの記録の扱い」
- 本文: 「この釉薬を使ったテストピースが N 件あります。記録済みの調合をどうしますか？ 調合を改良した場合は、複製して別の釉薬にすると系統が残ります。」
- 選択肢: 「キャンセル」「記録はそのまま」「記録も直す」

「キャンセル」は保存を中止して編集画面に留まる。「記録はそのまま」は釉薬だけを保存する。過去のテストピースには元の調合が残り、詳細画面には「釉薬の現在の調合とは異なります。」が出る。「記録も直す」は釉薬を保存し、該当するテストピースの写しのうち、この釉薬の部分を新しい調合に置き換える（`source` は `corrected`）。置き換えは第 3 章の `updateFieldsBatch` で行う。

ダイアログを待つのは利用者の操作であってサーバーの応答ではないので、楽観的な画面遷移の契約には反しない。選択のあとは従来通り、書き込みを待たずに画面を閉じる。

釉薬名だけを変えた場合はダイアログを出さない。名前は現在の値を表示する規則（第 3 章）なので、過去の表示にも自然に反映される。

### テスト

## 5. 評価とピースの番号

### 現状と問題

## 6. 焼成回

### 現状と問題

テストピースが持つ焼成の情報は、焼成プロファイルと焼成雰囲気への参照だけである。焼成プロファイルは繰り返し使う計画のひな形であり、いつ焼いたか、どの窯で焼いたか、実際にどう焼けたかを残す場所はない。テストピースが持つ日付は登録日時（`createdAt`）だけで、後日まとめて登録すれば焼いた日とは食い違う。同じ窯で一緒に焼いたテストピースであることも記録に残らない。そして、同じ窯で焼いた 30 枚を登録するとき、同じ焼成条件を 30 回選び直すことになる。

### 方針

焼成回という実体を新設する。焼成回は、焼いた日、窯の名前、計画として使った焼成プロファイル、焼成雰囲気、実績の覚え書きを持つ。テストピースは焼成回を任意で参照する。同じ窯で焼いたテストピースの焼成条件は、焼成回に一度入力すれば済む。

焼成回を参照するテストピースでは、焼成の情報は焼成回だけを正とする。テストピースが持つ既存の焼成プロファイルと焼成雰囲気の参照は、焼成回を参照しないテストピースでだけ使う。新しい記録で両方を持つことはしない。

### データの形

`lib/models/firing.dart` を新設する。

```dart
class Firing {
  final String? id;
  final Timestamp firedOn;            // 焼成日。その日の正午（端末の時刻）で保存する
  final String? kilnName;             // 窯の名前（自由入力）
  final String? firingProfileId;      // 計画として使った焼成プロファイル
  final FiringProfileSnapshot? profile; // その時点のプロファイルの写し
  final String? firingAtmosphereId;
  final String? atmosphereName;       // その時点の雰囲気名
  final String? atmosphereType;       // その時点の FiringAtmosphereType.name
  final int? peakTemp;                // 実測の最高温度 (℃)
  final String? cone;                 // コーンの結果（自由入力）
  final String? note;                 // 所感
  final Timestamp createdAt;

  /// 一覧やグループの見出しに使う表示名。例: '2026/11/8 電気窯'
  String get displayLabel;
}

class FiringProfileSnapshot {
  final String name;
  final String? curveData;
  final bool isReduction;
  final int? reductionStartTemp;
  final int? reductionEndTemp;
}
```

焼成日を正午で保存するのは、時刻を持たない日付を `Timestamp` で表すときに、端末の時間帯の違いで日付がずれるのを避けるためである。表示は年月日だけを使う。日付の書式は、共有画像が使っている手書きの整形（`test_piece_share_screen.dart` 193-194 行の `'${d.year}/${d.month}/${d.day}'`）に合わせる。この整形を `lib/utils/date_format.dart` の `String formatDate(DateTime)` に切り出し、共有画像もこれを使うようにする。`intl` は依存に入っていないので足さない。

焼成プロファイルの写しを持つのは、調合の写しと同じ理由である。プロファイルは繰り返し編集されるひな形であり、ID の参照だけでは、その日の計画が後から変わってしまう。

`lib/models/test_piece.dart` に `final String? firingId;` を足す。`toFirestore` は、値が null でも `'firingId': firingId` を出力すること。第 2 章の `toUpdateFields` は `toFirestore` から作るので、null のときに出力を省くと、焼成回を「（なし）」に戻して保存しても、文書の `firingId` が消えない。`firingAtmosphereId` と `firingProfileId` が現在そうしているのと同じ書き方である。

リポジトリは `lib/repositories/firing_repository.dart` を新設する。`lib/repositories/firing_profile_repository.dart` が最小の手本である。コレクション名は `firings`、並びは `orderBy('firedOn', descending: true)` とする。焼成回は、作成した直後にその ID をテストピースに持たせる使い方があるので、`TestPieceRepository` の `newDocumentId()` と `setById()` と同じ 2 つのメソッドを持たせる。

`lib/services/firestore_service.dart` に、ほかのマスタと同じ形でメソッド群を足す。`createFiringId`、`setFiring`、`getFirings`、`getFiringsOnce`、`updateFiring`、`deleteFiring` である。`lib/providers/data_providers.dart` に `firingsProvider`（一覧の購読）と `firingMapProvider`（ID からモデルを引く Map）を、ほかのプロバイダと同じ書き方で足す。

### 焼成の情報の解決

テストピースの焼成の情報は、焼成回を参照するかどうかで出所が変わる。この判断を画面ごとに書くと必ずずれるので、一つの純関数にまとめる。第 3 章で作った `lib/utils/test_piece_display.dart` に足す。

```dart
class ResolvedFiring {
  final Firing? firing;           // 参照する焼成回（なければ null）
  final bool firingMissing;       // firingId はあるが焼成回が見つからない
  final DateTime? firedOn;
  final String? kilnName;
  final String? atmosphereName;
  final FiringAtmosphereType atmosphereType;
  final String? profileName;
  final String? curveData;
  final bool isReduction;
  final int? reductionStartTemp;
  final int? reductionEndTemp;
}

ResolvedFiring resolveFiring(
  TestPiece piece, {
  required Map<String, Firing> firingMap,
  required Map<String, FiringAtmosphere> atmosphereMap,
  required Map<String, FiringProfile> profileMap,
})
```

規則は次の通りである。

テストピースに `firingId` があり、焼成回が見つかる場合。雰囲気の名前と種類は、雰囲気が現存すれば現在の値を、なければ焼成回の写しの値を使う。プロファイルの名前は、プロファイルが現存すれば現在の名前を、なければ写しの名前を使う。温度曲線と還元の値は、常に焼成回の写しを使う。写しがない場合（プロファイルを選ばずに作った焼成回）は null とする。

テストピースに `firingId` があるが、焼成回が見つからない場合（削除された）。`firingMissing` を true にし、`atmosphereType` を `FiringAtmosphereType.other`、`isReduction` を false、ほかはすべて null とする。

テストピースに `firingId` がない場合。従来通り、テストピースの `firingAtmosphereId` と `firingProfileId` から現在の値を引く。

表示の文言は、値が null のとき「未設定」、`firingMissing` のとき「不明」とする。現在のカードは、雰囲気やプロファイルが未設定でも「不明な雰囲気」「不明なプロファイル」と表示している（`test_piece_grid.dart` 62、66 行）。これも「未設定」に直す。

## 7. 比較表示

### 現状と問題

テストピースどうしを比べる画面がない。違いを見るには、詳細画面を行き来して覚えておくしかない。釉薬の試験で知りたいのは「何を変えたら、何が変わったか」であり、これが最も必要な画面である。

### 方針

一覧のグリッドで 2〜4 枚を選び、比較の画面で並べる。写真を横に並べ、各項目のうち値の違うものを目立たせる。調合は原料ごとに量を並べて差を示す。新しい入力は何も要求しない。

この画面が示すのは違いであって、結果を変えた原因ではない。記録のない項目を「同じ」と表示してはならない。

### 調合の差の計算

純関数を `lib/utils/recipe_diff.dart` に置く。

```dart
class RecipeDiffRow {
  final String materialId;
  final List<double?> amounts;     // 列ごとの重量。その列の調合に無ければ null
  final List<double?> percentages; // 列ごとの、合計に対する百分率
  final bool differs;              // 列の間で割合が違う
}

/// 複数の調合を原料ごとに並べる。
/// recipes の要素が null の列は「調合の記録なし」として扱い、違いの判定から除く。
List<RecipeDiffRow> diffRecipes(
  List<Map<String, double>?> recipes, {
  double tolerancePercent = 0.05,
})
```

違いの判定は、重量そのものではなく、合計に対する割合で行う。調合は重量で書かれており、同じ調合でも一度に作る量が違えば重量は違うからである。割合の差が `tolerancePercent` 以上なら違うとする。ある列にその原料がなく、別の列にあれば、違うとする。行の並びは、先頭の列の重量の多い順とし、先頭の列にない原料はその後ろに置く。

## 8. アップロード待ちの永続化

### 現状と問題

写真のアップロードは、Firestore への書き込みがサーバーに届いたあとで始まる（`lib/screens/test_piece_edit_screen.dart` 183-204 行の `writeFuture.then(...)`）。Cloud Functions は画像のアップロードを受けてテストピースの文書を探すので、文書が先にサーバーにある必要があるからである。それまで、画像のバイト列は編集画面の State から渡されたメモリ上の値として待つ。オフラインのあいだは書き込みが完了しないので、アップロードも始まらない。そのままアプリを閉じると、文書だけが後で同期され、写真は付かないままになる。付いていないことは利用者に知らされない。

現在の作りには、この欠落を言い訳する画面もある。詳細画面から編集へ進むとき、オフラインだと「現在オフラインのため、画像のアップロードはできません。テキスト情報のみ保存可能です。」というダイアログが出る（`test_piece_detail_screen.dart` 414-451 行）。オフライン対応を必須要件とするアプリとして、これは直すべき箇所である。

第 9 章でカメラからの直接撮影を入れると、アプリが持っている画像が唯一の原本になる。永続化はその前提である。

### 方針

選んだ画像を端末内の保存領域に書き、アップロード待ちの情報と一緒に残す。アップロードが済むまで消さない。アプリの起動時、通信の回復時、アプリが前面に戻ったときに、待ちになっているものを順に送る。アプリが終了しているあいだに送り続けることまでは求めず、次に起動したときに再開されることを保証する。

アップロード待ちの写真は、一覧でも詳細でも端末内の画像をそのまま表示し、まだ送られていないことが分かる印を付ける。

### 保存の層

`lib/services/pending_upload_store.dart` を新設する。

```dart
class PendingUpload {
  final String uid;
  final String testPieceId;
  final String fileName;     // アップロード先のファイル名
  final String storagePath;  // アップロード先のパス（テストピースの imagePath と同じ値）
  final String localPath;    // 端末内の画像ファイルのパス
  final DateTime createdAt;
  final int attempts;
  final String? lastError;
}

class PendingUploadStore {
  /// 保存先のディレクトリを返す関数を注入できるようにする（テスト用）。
  PendingUploadStore({Future<Directory> Function()? baseDirectory});

  Future<List<PendingUpload>> loadAll();
  Future<PendingUpload> save({uid, testPieceId, fileName, storagePath, bytes});

  /// テストピースの待ちを無条件に消す（テストピースの削除時）。
  Future<void> remove(String testPieceId);

  /// 現在の待ちの storagePath が一致するときだけ消す（送信の完了時）。
  Future<void> removeIfCurrent(String testPieceId, String storagePath);

  Future<void> recordFailure(String testPieceId, String storagePath, String error);
}
```

保存先は `path_provider` の `getApplicationSupportDirectory()` の下の `pending_uploads/{testPieceId}/` とし、画像を `fileName` の名前で、情報を `job.json` として置く。`path_provider` は依存に入っているが、これまで lib で使われていない。Windows、macOS、Android の 3 つで動くことを実機で確かめること。

待ちは 1 枚のテストピースにつき 1 つとする。同じテストピースの画像を選び直して保存したら、古い待ちとその画像を消し、新しい待ちに置き換える。

置き換えは、古い画像の送信の最中にも起こりうる。画像 A を送っているあいだに利用者が画像 B を選んで保存すると、待ちは B に置き換わる。そのあとで A の送信が終わったとき、テストピースの ID だけを見て待ちを消すと、B の待ちと画像を消してしまう。送信の完了と失敗の記録は、必ず `storagePath` を添えて行い、現在の待ちが同じ `storagePath` のものであるときだけ反映すること（`removeIfCurrent` と `recordFailure` の引数はそのためにある）。画像のファイル名を固定の名前にせず `fileName` にしているのも、A と B の画像を取り違えないためである。

### 送信の層

`lib/services/upload_queue.dart` を新設する。`ChangeNotifier` とし、`lib/providers/data_providers.dart` に `uploadQueueProvider`（`ChangeNotifierProvider`）を足す。設定のサービスと同じ形である。

```dart
class UploadQueue extends ChangeNotifier {
  /// テストピース ID → アップロード待ち。現在の利用者のものだけ。
  Map<String, PendingUpload> get pending;

  Future<void> enqueue({testPieceId, fileName, storagePath, bytes});
  Future<void> remove(String testPieceId);

  /// 待ちになっているものを順に送る。実行中に呼ばれたら何もしない。
  Future<void> processAll();
}
```

`processAll` は、現在サインインしている利用者の待ちについて、1 件ずつ次を行う。

まず、テストピースの文書をサーバーから読む（`collection.doc(id).get(const GetOptions(source: Source.server))`）。ここには注意が要る。`Source.server` の読み取りは、サーバーに届かなければ失敗するが、成功したときに返る内容には、端末に残っている未送信の書き込みが重ねられている（`cloud_firestore_platform_interface` の `GetOptions` の説明にある通り、遅延補償が効く）。したがって「文書が存在し、`imagePath` が一致する」だけでは、その書き込みがサーバーに届いたことにならない。届いたかどうかは `snapshot.metadata.hasPendingWrites` で見分ける。

読み取りの結果で 5 つに分かれる。

1. 読み取りが失敗する。通信できないので、そこで処理全体を打ち切る。
2. 文書が存在しない。未送信の書き込みもないということなので、テストピースは削除されている。待ちを捨てる。
3. 文書は存在するが、`hasPendingWrites` が true である。文書の書き込みがまだサーバーに届いていない。待ちを残して次へ進む。
4. 文書が存在し、未送信の書き込みはなく、`imagePath` が待ちの `storagePath` と違う。画像が選び直されたか外されたので、待ちを捨てる。
5. 文書が存在し、未送信の書き込みはなく、`imagePath` が一致する。端末内の画像を読んで `StorageService.uploadTestPieceImage` で送る。成功したら `removeIfCurrent` で待ちと画像を消す。失敗したら `recordFailure` で記録して残す。

3 の判定を省いてはならない。省くと、既存のテストピースの画像を差し替えたときに、`imagePath` の更新がサーバーに届く前にアップロードが始まる。Cloud Functions が文書を読んだ時点で `imagePath` がまだ古ければ、後述の照合が新しい画像を「古い処理」と判断して削除してしまう。

この「書き込みがサーバーに届いたことを確かめてから送る」という順序は、現在の「書き込みの完了を待ってから送る」と同じ条件を、アプリの再起動をまたいでも守るためのものである。端末のキャッシュだけを読む `Source.cache` は使わない。キャッシュに文書がないと、存在しないという結果ではなくエラーになり、通信できない場合と区別できないからである。

テストしやすいように、「文書の状態を調べる」処理と「送る」処理はコンストラクタで関数として注入できるようにする。文書の状態は `enum`（通信不可、削除済み、同期待ち、古い、送信可）で返す形にするとよい。

`UploadQueue` のコンストラクタでは、`path_provider` や `FirebaseAuth` に触れてはならない。待ちの読み込みは、`MainTabScreen` が明示的に呼ぶ `load()` で行う。こうしておくと、`uploadQueueProvider` を読むだけのウィジェット（後述の `TestPieceImage`）は、テストでも差し替えなしで動く。現在の利用者の ID も、コンストラクタではなく、使うときに取得する関数として注入する。

1 回の `processAll` のあとに待ちが残っていて、通信は可能だった場合（文書の同期待ちが残った場合）は、20 秒後にもう一度 `processAll` を呼ぶ。待ちがなくなるか、通信できなくなったら止める。

`processAll` を呼ぶきっかけは次の 4 つである。`enqueue` の直後。`MainTabScreen` の `initState`（サインイン済みで画面が生成されたとき。`load()` に続けて呼ぶ）。通信の回復。アプリが前面に戻ったとき（`AppLifecycleListener` の `onResume`。これも `MainTabScreen` に置く）。

通信の回復は `connectivity_plus` の `Connectivity().onConnectivityChanged`（型は `Stream<List<ConnectivityResult>>`）で知る。現在は単発の `checkConnectivity()` しか使っていない。このストリームを `MainTabScreen` で直接購読すると、プラグインのないテスト環境で `MissingPluginException` が報告され、`MainTabScreen` のテストが落ちる。そこで `lib/providers/data_providers.dart` に `connectivityChangesProvider`（`StreamProvider<List<ConnectivityResult>>`）を足し、`MainTabScreen` は `ref.listenManual` でこれを監視する。テストではこのプロバイダを空のストリームに差し替える。

通信できないことによる失敗は、利用者に知らせない。印が付いているので分かる。それ以外の理由で送信に失敗したときは、SnackBar で「写真のアップロードに失敗しました。あとで再試行します。」と知らせる。`processAll` は編集画面とは無関係に動くので、画面の `ScaffoldMessenger` を使えない。`lib/main.dart` に `scaffoldMessengerKey`（`GlobalKey<ScaffoldMessengerState>`）を足して `MaterialApp` に渡し、これを使う。現在の `main.dart` には `navigatorKey` しかない（14 行）。

### 保存の流れの変更

編集画面の保存処理（183-211 行）を次の順に変える。

1. 新しい画像があれば、`await uploadQueue.enqueue(...)` で端末に保存する。端末内への書き込みなので、すぐに終わる。
2. Firestore への書き込みを発火する。待たない。失敗は SnackBar で知らせる（従来通り）。
3. 画面を閉じる。

`enqueue` は端末への保存を終えたあと、`processAll` を待たずに呼ぶ。`writeFuture.then(...)` でアップロードを始める現在の処理（191-204 行）は削除する。

端末への保存を待ってから画面を閉じるので、厳密には「待たずに閉じる」ではなくなる。しかし待つのは端末内の書き込みであり、サーバーとの往復ではない。AGENTS.md の契約（成功時の画面遷移をサーバーとの往復で待たせない）には反しない。

テストピースの削除（`_confirmDelete`、224-287 行）では、`uploadQueue.remove(id)` も呼ぶ。

詳細画面から編集へ進むときのオフラインの警告（`_navigateToEditScreen`、414-451 行）は削除し、そのまま編集画面へ進むようにする。オフラインでも写真を選んで保存できるようになるからである。

`docs/spec.md` §5 の「テストピース保存フロー」を、この流れに書き換える。

### Cloud Functions の変更

`functions/image_pipeline.py` の書き戻し（243-258 行）は、処理中の画像がテストピースの現在の画像であるかを確かめない。新しい形式のパスでは、パスに含まれる文書 ID で文書を引くだけで、文書の `imagePath` を見ない。そのあとの掃除（265-278 行）は、処理中の画像とそのサムネイル以外を、同じテストピースのフォルダからすべて削除する。

このため、同じテストピースの画像が短い間隔で 2 度アップロードされ、処理の順が前後すると、古い画像の URL が文書に書かれ、新しい画像のファイルが削除されうる。再送が入るとこの状況は起きやすくなる。

トランザクションの中で照合する。`_write_back` で文書を読んだ直後に、文書の `imagePath` を調べる。新しい形式のパス（`doc_id` が None でない）で、文書の `imagePath` が空でない文字列であり、処理中のファイルのパス（`file_path`）と違う場合は、古い処理と判断する。古い処理では、文書を更新しない。`_write_back` の戻り値を、色を書いたかどうかの真偽値から、結果を表す値（更新した、古かった）に変える。

古かった場合は、掃除（265-278 行）を行わず、代わりに処理中の画像と、いま作ったサムネイルを削除する。文書はこれらを参照していないからである。

照合だけでは防げない順序が一つ残る。画像 A の処理が照合を通って文書を更新したあと、掃除に入るまでのあいだに、利用者が画像 B に差し替え、B がアップロードされる場合である。現在の掃除は「処理中の画像とそのサムネイル以外をすべて削除する」ので、A の掃除が B を削除してしまう。これを防ぐため、掃除の対象を「処理中の画像より古いもの」に限る。`images/{doc_id}/` の下のファイルは、作成時刻（blob の `time_created`）が処理中の画像より前のものだけを削除する。`thumbnails/{doc_id}/` の下のサムネイルは、名前（`thumb_` に元の画像のファイル名を続けたもの）が、削除せずに残した画像のどれにも対応しないものだけを削除する。こうすると、A の掃除は自分より新しい B に触れず、B の処理が終わったときに B の掃除が A を消す。

文書の `imagePath` が空の場合は、照合せずに従来通り更新する。古い形式のパス（`doc_id` が None）は、`imagePath` の一致で文書を探しているので、照合は要らない。

変更後、`functions/` で `python -m py_compile main.py image_pipeline.py transfer_codes.py` を通すこと。

**デプロイの順序。** 新しい Functions は、現在のクライアントとも正しく動く。現在のクライアントも、文書に `imagePath` を書いてから画像を送るからである。したがって Functions を先にデプロイしてよい。デプロイは利用者の指示を受けてから行う。

### エッジケース

サインアウトして別の利用者でサインインした場合、前の利用者の待ちは送らない。待ちは利用者の ID を持っており、`processAll` は現在の利用者のものだけを扱う。前の利用者が再びサインインすれば再開される。

端末内の画像が何らかの理由で消えていた場合は、待ちを捨てる。

画像を選び直して保存し、古い画像のアップロードがすでに始まっていた場合、古い画像が先にサーバーに届くことがある。Functions の照合がこれを古い処理と判断して捨てる。

Firestore の書き込みが恒久的に失敗した場合（権限がないなど）、端末の未送信の書き込みは取り消される。新規作成であれば文書は存在しなくなるので、待ちは「削除済み」として捨てられる。

### テスト

`test/services/pending_upload_store_test.dart` を新設する。一時ディレクトリを注入し、保存・読み込み・置き換え・削除を確かめる。`test/services/upload_queue_test.dart` を新設する。文書の状態を返す関数と送る関数を差し替え、5 つの状態それぞれの動き、送信の失敗が記録されること、別の利用者の待ちを扱わないことを確かめる。`TestPieceImage` のウィジェットテストを新設する（4 つの表示）。`test/screens/test_piece_edit_screen_test.dart` に、新しい画像を持って保存すると `enqueue` が呼ばれ、`uploadTestPieceImage` が画面からは直接呼ばれないことを足す。

既存のテストにも手が入る。`TestPieceImage` は `ConsumerWidget` なので、これを含むウィジェットは `ProviderScope` の下で組み立てる必要がある。`test/widgets/test_piece_card_test.dart` と `test/widgets/test_piece_grid_test.dart` には、`ProviderScope` なしで `TestPieceCard` や `TestPieceGrid` を組み立てているテストがあり、そのままでは「No ProviderScope found」で落ちる。`ProviderScope` で包むこと。`UploadQueue` のコンストラクタがプラグインに触れない作りであれば、差し替えは要らない。`test/screens/main_tab_screen_test.dart` は、`MainTabScreen` が `load()` と通信の監視を行うようになるので、`uploadQueueProvider` をプラグインに触れない偽物に、`connectivityChangesProvider` を空のストリームに差し替える。

Functions にはテストの仕組みがない。照合の判断を `image_pipeline.py` の中の小さな純関数（文書の `imagePath`、処理中のパス、`doc_id` を受け取り、古いかどうかを返す）に切り出し、その関数だけを確かめる短いテストを `functions/test_image_pipeline.py` として足す。標準の `unittest` で書き、追加の依存は入れない。

## 9. 入力の作り直し

### 現状と問題

テストピースの登録は、一覧の右下のボタンから白紙の編集画面を開くところから始まる（`lib/screens/test_piece_list_screen.dart` 104-117 行）。保存すると画面は必ず閉じ、次の 1 枚はまた白紙から始まる。同じ窯で焼いた 30 枚は素地土も焼成条件もほぼ共通だが、毎回選び直すことになる。釉薬の詳細画面から、その釉薬のテストピースを追加する導線もない。写真の取得元はギャラリーに固定されており（`test_piece_edit_screen.dart` 91 行の `ImageSource.gallery`）、カメラで直接撮ることも、複数枚をまとめて選ぶこともできない。

### 方針

4 つを足す。文脈を引き継いで編集画面を開く入口。保存したあと、条件を引き継いで次の 1 枚へ進む連続登録。スマホでのカメラからの直接撮影。複数の写真をまとめて選び、1 枚ずつ連続して登録する流れ。

利用者は、窯入れ前に写真なしで登録する使い方と、焼成後に写真から登録する使い方の両方を使う。どちらも同じ編集画面で扱う。写真は以前から任意なので、前者は第 6 章の焼成回と本章の連続登録で、そのまま成り立つ。

### 編集画面の入口

`TestPieceEditScreen` のコンストラクタ（25-33 行）に、新規作成のときの初期値を足す。

```dart
const TestPieceEditScreen({
  super.key,
  this.testPiece,
  this.initialGlazeId,
  this.initialAdditionalGlazeIds = const [],
  this.initialClayId,
  this.initialFiringId,
  this.initialFiringAtmosphereId,
  this.initialFiringProfileId,
  this.initialLabel,
  this.queuedImages = const [],
});
```

`initState`（60-73 行）で、`testPiece` が null のときに限り、これらを State の初期値に入れる。`queuedImages` は後述の一括選択で使う。

入口を 2 つ足す。釉薬の詳細画面の関連テストピースの節（`glaze_detail_screen.dart` の `_buildTestPiecesSection`、136-209 行）の見出しの横に「テストピースを追加」のテキストボタンを置き、`TestPieceEditScreen(initialGlazeId: glaze.id)` へ遷移する。焼成回の詳細画面の FAB は第 6 章で足してある。

### 連続登録

新規作成のとき（`widget.testPiece == null`）に限り、フォームの最後に「保存して次を登録」のボタン（`OutlinedButton`）を足す。AppBar の保存ボタン（`CommonAppBarActions`）は従来通り、保存して閉じる。

保存処理 `_saveTestPiece` に `bool continueNext` の引数を足す。保存の中身は同じで、最後の画面遷移だけが違う。`continueNext` が true のときは、`navigator.pop()`（214 行）の代わりに `navigator.pushReplacement` で新しい `TestPieceEditScreen` を開き、次の値を引き継ぐ。主たる釉薬。追加釉薬。素地土。焼成回（選んでいなければ、焼成雰囲気と焼成プロファイル）。番号の次の候補。残りの写真。

写真、色、評価、備考は引き継がない。

釉薬も引き継ぐのは、同じ釉薬を別の素地土に掛けた試験と、別の釉薬を同じ素地土に掛けた試験の、どちらもあるからである。違うものだけを選び直せばよい。

番号の次の候補は、純関数 `lib/utils/label_increment.dart` の `String? nextLabel(String? label)` で作る。番号の末尾が数字なら、その数字を 1 増やして返す。桁数は保つ（「1108-03」は「1108-04」、「1108-09」は「1108-10」）。末尾が数字でなければ null を返す（次の画面の番号欄は空になる）。利用者の付け方は「日付＋番号」なので、これで合う。重複のチェックはしない。

### カメラからの直接撮影

`_pickImage`（87-125 行）を変える。Android では、写真を選ぶボタンを押すと `showModalBottomSheet` で「カメラで撮影」と「ギャラリーから選択」の 2 つを出し、選ばれたほうの `ImageSource` で `pickImage` を呼ぶ。プラットフォームの判定は `!kIsWeb && Platform.isAndroid` とする。Windows と macOS では従来通り、すぐにファイルの選択を開く。デスクトップのカメラは `image_picker` が対応していないので対象にしない。iOS はこのアプリの対象の OS ではなく、`ios/Runner/Info.plist` にカメラの利用目的の記述（`NSCameraUsageDescription`）もないので、カメラの選択肢は出さない。

`maxWidth` と `maxHeight` の 1500（92-93 行）、ファイル名の決め方、切り抜きの画面への遷移は変えない。ボタンのラベル（561 行付近の「ギャラリーから画像を選択」）は「写真を選択」に直す。

Android では、カメラのアプリを開いているあいだに、メモリの不足でこちらのアプリの画面が破棄されることがある。`image_picker` はこの場合の復元の手段（`retrieveLostData`）を用意している。`MainTabScreen` の `initState` で、Android のときだけ `ImagePicker().retrieveLostData()` を呼び、画像が返ってきたら `TestPieceEditScreen(queuedImages: [画像])` を開く。入力していたほかの項目は失われるが、撮った写真は失われない。

Android のマニフェスト（`android/app/src/main/AndroidManifest.xml`）には現在、権限の宣言が一つもない。`image_picker` のカメラは、アプリが `CAMERA` の権限を宣言していなければ権限なしで動くので、宣言は足さない。実機で撮影できることを確かめること。

### 複数の写真の一括選択

編集画面の画像の節（`_buildImageSection`、553-566 行）に、新規作成のときに限り、「複数の写真を選んで連続登録」のテキストボタンを足す。押すと `ImagePicker().pickMultiImage(maxWidth: 1500, maxHeight: 1500)` を呼ぶ。選ばれた写真のうち 1 枚目を、通常の選択と同じ流れ（切り抜きの画面）に通して、いま開いている画面の写真にする。2 枚目以降は State の `List<XFile> _queuedImages` に持つ。

残りの写真があるあいだ、「保存して次を登録」のボタンのラベルを「保存して次を登録（残り N 枚）」にする。このボタンで次の画面へ進むとき、`queuedImages` に残りの写真を渡す。

`initState` で `queuedImages` が空でなければ、最初のフレームのあと（`WidgetsBinding.instance.addPostFrameCallback`）に、先頭の写真で切り抜きの画面を自動で開く。切り抜きを確定したらその写真をこの画面の写真にし、残りを `_queuedImages` に持つ。切り抜きをやめて戻ったら、その写真は使わず、残りはそのまま持つ。

これにより、撮りためた 30 枚を一度に選び、1 枚ごとに切り抜いて釉薬を選び、「保存して次を登録」を押す、という流れで登録できる。素地土と焼成回は最初の 1 枚で選べば引き継がれる。

残りの写真があるまま AppBar の保存ボタンで閉じた場合、残りは捨てられる。残りがあるときに閉じようとしたら、確認を出す（「残り N 枚の写真は登録されません。閉じますか？」）。未保存の確認（`UnsavedChangesPopScope`）とは別の確認である。

### エッジケース

「保存して次を登録」は、保存の検証（釉薬と素地土が必須）に通らなければ次へ進まない。

連続登録の途中でも、各テストピースの保存は 1 枚ずつ完結している。途中でやめても、それまでの登録は残る。

一括選択した写真は、切り抜くまで端末内の元のファイルを参照している。切り抜いて保存した時点で、第 8 章のアップロード待ちとして端末内に写される。

### テスト

`test/utils/label_increment_test.dart` を新設する（桁数の保持、繰り上がり、末尾が数字でない場合、null と空文字列）。`test/screens/test_piece_edit_screen_test.dart` に、初期値が反映されること、「保存して次を登録」で保存が呼ばれ、新しい編集画面が素地土と釉薬を引き継いで開くこと、既存のテストピースの編集ではこのボタンが出ないことを足す。`image_picker` を使う部分は既存のテストでも差し替えていないので、カメラと一括選択は実機で確かめる。

## 10. 全データの書き出し

### 現状と問題

利用者が自分の記録をアプリの外へ取り出す手段がない。記録は開発者の Firebase プロジェクトの中にだけある。取り出すには Firebase のコンソールを使うか、スクリプトを書くしかない。`docs/spec.md` §6 の将来候補には「データエクスポート: Excel / CSV 書き出し（バックアップ用途）」がある。

### 方針

設定画面から、全データを 1 つの ZIP ファイルに書き出す。中身は 3 種類である。機械が読める JSON（全コレクション）。人が表計算ソフトで開ける Excel ファイル。テストピースの写真の実体。

本章を最後に置いたのは、前の章で足したフィールドとコレクションを含めて書き出すためである。

復元（ZIP から読み戻す）機能は作らない。書き出しの目的は、記録が利用者の手元にあることである。読み戻しが必要になったときは、JSON があれば後から道具を作れる。

### ZIP の中身

```
glaze_manager_export_20261110_1530.zip
├ data.json          全コレクション

├ images/
```

**data.json。** 次の形とする。

```json
{
  "formatVersion": 1,
  "exportedAt": "2026-11-10T06:30:00.000Z",
  "collections": {
    "materials": [ { "id": "...", ... } ],
    "glazes": [ ... ],
    "clays": [ ... ],
    "firingProfiles": [ ... ],
    "firingAtmospheres": [ ... ],
    "firings": [ ... ],
    "tags": [ "..." ],
    "testPieces": [ ... ]
  },
  "missingImages": [ "テストピースID", ... ]
}
```

各文書は、モデルの `toFirestore()` の Map に `id` を足したものとする。`Timestamp` は JSON にできないので、ISO 8601 の文字列（UTC）に変える。Map と List の中も再帰的に変える。タグは名前の一覧である（`getTagsOnce` が返すもの）。閲覧履歴は含めない。

**glaze_manager.xlsx。** `excel` パッケージ（4.0.6）で作る。取り込みのテスト（`test/services/glaze_import_service_test.dart` 7-12 行）が `Excel.createExcel()`、`appendRow`、`save()` を使っているので、同じ API で書ける。シートは 4 つとする。

「釉薬」のシートは先頭に置き、既存の取り込み（`lib/services/glaze_import_service.dart`）がそのまま読める形にする。取り込みは先頭のシートだけを読み、1 行目の見出しが「釉薬名、登録名、原料名…、顔料、（任意の列）、備考」であることを求める（103-120 行）。そこで見出しを「釉薬名、登録名、（顔料以外の原料の名前を、いずれかの釉薬で使われているものだけ）、顔料、タグ、備考」とする。各行は、原料の列にその釉薬の量を入れ（使っていなければ空）、顔料の列に取り込みが読める書式で入れ、タグの列にタグを読点でつなぎ、備考の列に備考を入れる。

顔料の列の書式は「弁柄 8, 呉須 2」のように、名前、半角スペース、量を続けたものをカンマで区切る。取り込みは各項目を、末尾の数字とそれより前の名前に分け、名前の前後の空白を除く（165-181 行）。名前と量のあいだにスペースを入れずに「顔料18」と書くと、名前が「顔料1」で量が 8 なのか、名前が「顔料」で量が 18 なのかを区別できない。スペースを入れれば、数字で終わる名前の顔料も正しく往復する。量は `RecipeTable.formatAmount` と同じく、整数なら小数点なしで書く。

`Excel.createExcel()` は、既定のシート「Sheet1」を持った状態でブックを作る。新しいシートを足すだけでは、空の Sheet1 が先頭に残り、取り込みは「データが含まれていません」で失敗する。既定のシートを `excel.rename(...)` で「釉薬」に改名して使い、ほかの 3 つのシートをそのあとに足すこと。

取り込みとの往復には、既存の取り込みの仕様から来る限界が 3 つある。書き出しの側では対処せず、そういうものとして扱う。顔料以外の原料の列が一つもない場合、見出しが 5 列になり、取り込みの検証（6 列以上）を通らない。添加剤のカテゴリの原料は原料の列に入るので、取り込み先に同じ名前の原料がなければ、母剤として作られる。調合が空の釉薬は、取り込みで捨てられる。

「テストピース」のシートは、1 行に 1 枚で、番号、釉薬、追加釉薬、素地土、焼成日、窯、焼成雰囲気、焼成プロファイル、評価、備考、登録日、画像のファイル名、調合（写しの各行を「長石 500 / 土灰 300」のようにつないだ文字列）を入れる。値は画面と同じ解決の関数で得る。

「原料」のシートは、名前、カテゴリ、そして成分の列（いずれかの原料に登録されている成分名を横に並べる）とする。

「焼成回」のシートは、焼成日、窯、焼成雰囲気、焼成プロファイル、最高温度、コーン、所感とする。

**images。** テストピースごとに 1 枚、原寸の画像を入れる。取得の順は次の通りである。第 8 章のアップロード待ちがあれば、端末内の画像を使う。なければ、`imageUrl` があれば `http` パッケージの `get` で取得する。`imageUrl` はトークンの付いたダウンロード用の URL である（`functions/image_pipeline.py` 20-27 行）。`http` は引き継ぎコードの処理で Windows でも使われている（`lib/services/auth_service.dart`）。`imageUrl` がなく `imagePath` があれば、`firebase_storage` の `ref(imagePath).getData()` で取得する。どれでも取得できなければ、`missingImages` にテストピースの ID を足す。写真のないテストピース（`imagePath` も `imageUrl` もない）は、取得できなかったものには数えない。

取得できなかった写真があることを、書き出しの完了の通知で利用者に知らせる。取得できたものだけを黙って書き出して、全件であるかのように見せてはならない。

### 実装

`pubspec.yaml` の dependencies に `archive` を足す。`pubspec.lock` にはすでに間接依存として 3.6.1 が入っているので、同じ版の範囲（`^3.6.1`）で宣言する。直接 import するには直接の依存にする必要がある。

`lib/services/data_exporter.dart` を新設する。

```dart
class ExportProgress {
  final String message; // 例: '写真を取得しています (12/87)'
}

class ExportResult {
  final File zipFile;
  final int testPieceCount;
  final int missingImageCount;
}

class DataExporter {
  DataExporter({
    required FirestoreService firestoreService,
    required UploadQueue uploadQueue,
    http.Client? httpClient,
    FirebaseStorage? storage,
  });

  /// workDir の下に ZIP を作って返す。
  Future<ExportResult> export({
    required Directory workDir,
    void Function(ExportProgress)? onProgress,
  });
}
```

手順は次の通りである。各コレクションを `FirestoreService` の `get…Once` で 1 回ずつ取得する。`workDir` の下に `content` というディレクトリを作り、そこに `data.json` と `glaze_manager.xlsx` を書く。写真を 1 枚ずつ取得して `content/images/` に書く。メモリに溜め込まず、1 枚ごとにファイルへ書く。`archive` の `ZipFileEncoder`（`package:archive/archive_io.dart`）の `zipDirectory` で `content` の中身を ZIP にまとめる。ZIP の出力先は `workDir` の直下（`content` の隣）にする。archive 3.6.1 は、出力先が圧縮するディレクトリの中にあると `FormatException` を投げるからである。

Excel の中身を作る部分と、JSON に変える部分は、ファイルの入出力から切り離した純関数にする（`Uint8List buildExportWorkbook(...)`、`Object? toJsonSafe(Object? value)`）。テストはここを確かめる。

ZIP を利用者に渡す処理は、`lib/utils/png_exporter.dart` と同じ分岐にする。Android と iOS では `share_plus` で共有する（`XFile(zipFile.path, mimeType: 'application/zip')`）。Windows と macOS では `FilePicker.platform.saveFile` で保存先を選ばせ、ZIP をそこへ複写する。この分岐を `lib/utils/file_exporter.dart` に置く。作業用のディレクトリは `path_provider` の `getTemporaryDirectory()` の下に作り、渡し終えたら消す。

### 設定画面

`lib/screens/settings_screen.dart` の「データ管理」の節（86 行付近から。焼成プロファイル、焼成雰囲気、素地土名の管理の 3 項目が並ぶ）の最後に、「データの書き出し」の項目を足す。書き出しは画面の遷移ではなく、その場で実行する処理なので、進行の表示のために小さな `ConsumerStatefulWidget` に切り出す。同じ画面のアカウントの節（`_AccountSection`）が、`_isBusy` のフラグで処理中にスピナーへ差し替える作りになっているので、それに倣う。

項目は `ListTile` とし、題は「データの書き出し」、副題は「釉薬・テストピース・写真を ZIP ファイルに保存します」、右端のアイコンは `Icons.download_outlined` とする。処理中は副題を進行の文言（「写真を取得しています (12/87)」）に差し替え、右端をスピナーにし、タップを無効にする。

完了したら SnackBar で知らせる。文言は、デスクトップでは「データを書き出しました。」、取得できなかった写真があれば「データを書き出しました（写真 N 枚は取得できませんでした）。」とする。モバイルでは共有のシートが完了の表示を兼ねるので、取得できなかった写真があるときだけ知らせる。保存先の選択をやめた場合は何も出さない。失敗は「書き出しに失敗しました: …」とする。`ScaffoldMessenger` は、待つ処理の前に取得しておく（同じ画面の既存の処理と同じ）。

`test/screens/settings_screen_test.dart` は節の見出しの存在を確かめているが、見出しは増やさないので影響しない。

### エッジケース

オフラインで書き出すと、キャッシュにある文書は取得できるが、写真の大半は取得できない。取得できなかった枚数が通知に出る。

写真が多いと時間がかかる。進行の文言で枚数を示す。途中でやめる機能は作らない。

`imageUrl` のトークンは、Cloud Functions が同じ画像を再び処理すると変わる。書き出しの最中に変わることはまずないが、取得に失敗したら `imagePath` からの取得を試み、それでも駄目なら取得できなかったものに数える。

## 13. 実装時に変えた点

本書の 10 項目は 2026-11-10 にブランチ `test-notebook` へ実装した。実装のあとで ChatGPT 6.1 Sol にコードを照合させ、本書の指示のままでは記録や写真を失いうる箇所が見つかったので、次の点は本書と異なる実装にしてある。現在の正しい仕様は `docs/spec.md` §5 にある。本書の該当箇所を読むときは、こちらを優先すること。

**既存データへの調合の写しの適用（第 3 章）。** 本書は、購読中のプロバイダの値が揃ったら写しを埋める、としていた。しかし Firestore の購読は最初に端末のキャッシュを返すので、長く使っていなかった端末では「写しがない」と見えたまま書き込みが走り、別の端末ですでに保存された写しを、古い調合から作った写しで上書きしてしまう。そこで、判断に使う 4 つのコレクションをサーバーから読み（`UserScopedRepository.getAllFromServer`）、その内容で計画を立てて書き込む形にした（`FirestoreService.backfillTestPieceSnapshots`）。`snapshotBackfillPlanProvider` は作っていない。`MainTabScreen` は起動時にこれを呼び、通信できずに失敗したら、通信の回復時と前面復帰時にやり直す。

**アップロード待ちの送信（第 8 章）。** 四点を足した。文書を読んでいるあいだに利用者が切り替わった場合は、読んだ結果を使わずにその回を打ち切る（切り替わった先の利用者の領域を読んで「削除済み」と誤って判断し、前の利用者の待ちを捨てるのを防ぐ）。実行中に届いた送信の要求は、その回が通信不可で終わっても捨てずに処理する。通信できなかった場合は 60 秒ごとに試し直す（`connectivity_plus` の通知は接続の種類が変わったときにしか来ず、同じ接続のまま疎通だけが戻った場合には届かないため）。テストピースの削除では、文書の削除が済んでから端末内の待ちを消す。

**Cloud Functions の掃除（第 8 章）。** サムネイルの一覧を、画像の一覧より先に取る。逆の順だと、二つの一覧のあいだに処理を終えた新しい画像のサムネイルを、対応する画像がないものとして削除しうる。

**保存の二度押し（第 8 章、第 9 章）。** 端末内への写真の保存を待つようにしたことで、保存ボタンを続けて押すと二重に登録される隙ができた。編集画面に保存中のフラグを足して防いでいる。

**焼成回の削除（第 6 章）。** 本書は素地土の一覧と同じ try/catch を手本にしていたが、焼成回の削除は編集画面から行うので、完了を待つと画面遷移がサーバーの応答待ちになる。削除の完了を待たずに画面を閉じ、失敗は SnackBar で知らせる形にした。

照合で指摘されたが、直していない点が二つある。一つは、端末内への写真の保存が終わった直後、Firestore への書き込みを呼ぶ前にアプリが強制終了された場合で、次の起動時に文書が存在しないため待ちが捨てられる。この隙は処理の一行ぶんであり、その場合は記録そのものも保存されていないので、対処していない。もう一つは、二台の端末で同時に釉薬の編集の確認ダイアログを開き、両方で「記録も直す」を選んだ場合で、後から保存した側が、先に直された別の釉薬の写しを古い内容に戻しうる。利用者が一人であれば起きないので、対処していない。

### 実機での確認の結果（2026-11-11）

第 12 章の確認のうち Windows の分を、Firebase エミュレータ（デモ用のプロジェクト `demo-glaze-manager`）に実アプリを繋ぐ結合テストとして自動化し、通した。実プロジェクトと実データには触れていない。テストは `integration_test/` に、起動と実行の補助は `tool/emulator/` にある。実行の手順は `README.md` に書いた。

確かめられたことは次の通りである。写しを持たない既存の記録に、起動時に写しが埋まる。複数の写真を選んで連続登録でき、番号が 1 ずつ進む。写真は保存から 1 秒以内に送られ、Cloud Functions がサムネイルと色を書き戻す。既存のテストピースの写真を差し替えると、新しい写真だけが残る。釉薬の調合を変えたときの「記録はそのまま」と「記録も直す」、複製による派生が、サーバー上の文書に正しく反映される。焼成回の作成と割り当て、グループ表示、比較の画面が開く。書き出した ZIP に全テストピースの写真が入り、その Excel を既存の取り込みで読める。Firestore と Storage に届かない状態で写真つきで登録して終了し、起動し直すと、記録と写真がサーバーに届く。

`docs/価値向上方針.md` 第 11 章で未確認としていた「Windows で、オフラインのまま書き込んでアプリを再起動したあとも、書き込みが保持されるか」は、保持されることを確かめた。第 8 章が前提にした、`Source.server` の読み取りが未送信の書き込みを重ねて返すことも、実機で確かめた。Cloud Functions の照合と掃除は、エミュレータ上で 20 項目を確かめた（続けて 2 回差し替えても最後の画像が残る、古い画像が後から届いても文書は書き換えられない、手動の色を保つ、など）。

この確認で、遅れが二つ見つかり、直した。一つは、保存の直後の送信の試行が、ほぼ必ず文書がまだ未送信のうちに走るため、写真の送信が試し直しまで始まらなかった点である。編集画面は、文書の書き込みが完了した時点でも送信を始めるようにした。もう一つは、起動の直後にも同じことが起き、前回オフラインで登録した写真が届くまで約 20 秒かかっていた点である。同期待ちの試し直しの間隔を 20 秒から 3 秒に縮めた。同期待ちはサーバーに届く状態でしか起きず、長くは続かないので、短い間隔で差し支えない。

自動のテストでは確かめられず、人の手での確認が残っているのは、次の点である。Windows の firebase_storage による実際の送信（Windows の SDK は Storage のエミュレータに繋げないので、テストでは送信を REST に差し替えている）。写真の選択のダイアログ、書き出しの保存先のダイアログ。通信が実際に途切れて回復したときの通知。Android（カメラ、共有のシート、機内モード）と macOS。本番の Cloud Functions の、デプロイ後の動作（`process_uploaded_image` は 2026-11-11 に本番へデプロイした。本番での写真の登録と差し替えは、まだ試していない）。
